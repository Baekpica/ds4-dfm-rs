# GLM Prefill and partial offload on Spark

This campaign implements memory-fitted 2K batches, shared mixed-MoE
preparation and checkpoint-aligned SSD supply. Dense FP16 remains diagnostic.

This campaign starts at `d96840cbb1240ea80b809a02b0af8ab6c9f77662` and
compares upstream `0aaea5a238fb41a35106a551e73c8409dfb751ac` separately.
The mixed artifact is the [Uncensored recipe](glm53-uncensored.md).
Results apply to their recorded artifact, controls and workload.

## Execution and memory policy

`--ssd-streaming` remains Off by default. When enabled, omitted cache capacity
means `auto`; counts and GiB budgets remain available. Rust reserves mandatory
weights, active state, workspace, checkpoints, media and headroom before
spending the remainder on expert slots. Unsafe fixed capacities fail before
weight allocation. A cache batch uses its actual unique expert union;
duplicate routes do not consume additional slots.

Admission reports requested/effective width and cache capacity. The final
32K SSD receipt reports requested/effective 2048 and qualified `unverified`;
this campaign's artifact/workload records do not silently promote the old
family-wide serving qualification. Context and bank count remain requested
values while the memory fit can reduce physical width.

At the same 32768-token context and one bank, native graph accounting reports
180.02 MiB workspace at 128 rows and 2871.40 MiB at 2048 rows. The SSD 4K
window raises that to 3383.40 MiB. Active compact KV is 0.37 GiB and recurrent
state is 148.82 MiB in all three graphs; these figures exclude checkpoints,
MMQ temporary arenas and optional MTP/Vision. The 87.47 GiB GGUF remains
mmap-backed. Resident workers import 87.46 GiB of raw VMM weights from one
owner. Fixed partial offload instead keeps 3.97 GiB mandatory tensor spans
and 25768261500 bytes of expert slots, with 2.62 MiB staging per reader.
Mapped file size is not added to device residency as a second weight copy.

The first live Auto run selected all 12384 experts (87.69 GiB), but its
32K graph crossed the benchmark cgroup's 100 GiB `memory.high` boundary.
The guard stopped it at full PSI 21.43%, despite 21.19 GiB host MemAvailable;
this failed run is not qualified. GLM SSD admission now also limits available
bytes by each cgroup ancestor's `memory.high`/`memory.max` minus
`memory.current`. A parent includes sibling usage. The existing reserve stays
in the quote; this change does not impose an offload ratio. The failing-first
regression covers the high boundary, hard limit, parent usage, exhaustion and
unlimited groups. Linux defines high as a throttle/reclaim boundary and max
as a hard limit in its [cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory).

The layer-major path holds at most one checkpoint-aligned
4096-token window. Physical GEMMs remain at most 2048 rows. Two HC buffers
cost at most 512 MiB and are released after the window. Optional next-layer
reading uses two full-layer groups within the same expert pool, one bounded
pageable transfer buffer per reader, and a separate CUDA upload stream.
No large pinned host weight cache is added. Complete uploads become cache
entries only after joining the reader; eviction waits for GPU completion.
Cancellation and read/upload failure invalidate the unfinished frontier.

Short appends, two-bank execution and caches below two complete layers use
selected-expert supply. Prefill releases its transient reader/upload state;
expert slots remain the decode cache. The grouped path retains recent unique experts within each layer's funded
hot area. Recency spans physical chunks, and intermediate windows skip hot
copies when no logits frontier is requested. Full next-layer reads must be charged even when demand hits them.
Selected supply protects those recent routes during Prefill only when the
pool also has room for one complete layer; smaller pools retain ordinary LRU.

Native phase counters report hits/misses, unique routes, logical `pread_bytes`,
rereads, I/O/upload/join waits and full-tensor bytes. Process `read_bytes`
and `/usr/bin/time` filesystem inputs describe kernel-accounted storage I/O,
including startup and readahead. They are not logical pread volume, nor a
measurement of the SSD controller's NAND traffic. File-cache eviction remains
advisory.

## Reproduction

Build CUDA with `make cuda-spark`, then `make ds4-bench-perf`. The optional
NVTX build measures `ds4.prefill` and `ds4.decode` only. Use one raw VMM owner
for resident workers; stop that task-owned owner before standalone SSD or
upstream comparison. Run processes serially and preserve the clock range.

The resident benchmark imports raw weights from this task-owned owner:

```sh
./ds4_weight_server --base "$GLM_MODEL" --backend vmm --scope base \
  --manifest "$GLM_MANIFEST" --broker-socket "$GLM_BROKER" \
  --reserve-gb 24 --copy-chunk-mb 64 \
  --no-repack-iq2-aligned --no-repack-q2k-aligned --no-repack-q8-aligned
```

After its manifest/broker are ready, launch a fresh worker:

```sh
DS4_WEIGHT_RESIDENCY_BASE=eager \
DS4_CUDA_WEIGHT_IPC_MANIFEST="$GLM_MANIFEST" DS4_CUDA_WEIGHT_IPC_SCOPE=base \
DS4_GLM53_PREFILL_ROWS=2048 DS4_GLM53_DENSE_GEMM=0 \
DS4_GLM53_GATE_UP_PAIR=1 DS4_GLM53_LOW_ATTN_WIDE=1 \
DS4_GLM53_Q2_WORKLIST=0 DS4_MTP_SPEC_DISABLE=1 \
./ds4-bench-perf --cuda -m "$GLM_MODEL" \
  --prompt-file speed-bench/promessi_sposi.txt \
  --ctx-start 8192 --ctx-max 8192 --ctx-alloc 32768 \
  --gen-tokens 64 --mtp-draft 1 --mtp-margin 0 \
  --dump-frontier-logits-dir "$GLM_PROOF"
```

For fixed partial offload, stop the task owner and remove the three ownership
environment assignments from the worker command. Add
`--ssd-streaming --ssd-streaming-cache-experts 24GB --ssd-streaming-cold`.
Before each cold arm, advise eviction of only the task model file and verify
actual residency with `mincore`; never drop global caches. Use `auto` to test the
live memory policy separately. Window and next-layer supply are enabled
by default when eligible; `DS4_GLM53_PREFILL_WINDOW=0` and
`DS4_GLM53_PREFETCH=0` restore their reference supply paths.
`DS4_GLM53_GATE_UP_PAIR=0` and
`DS4_GLM53_LOW_ATTN_WIDE=0` restore the preparation/attention references.
`DS4_GLM53_DENSE_GEMM=1` exercises the rejected numerical candidate.

Run `make test-glm53-stream test-glm53-lifetime`, the GPU attention/pair/dense
fixtures, and the Rust state/MTP examples with the exact fixture artifact.
Keep cold workload state, slot-cache state, boot prewarm, process storage
bytes and observed clocks in every A/B receipt. Raw commands, per-run
controls, binary/source/prompt hashes, I/O counters and gate receipts are
retained in the machine-readable evidence linked below.

[Machine-readable evidence](evidence/glm53-prefill-2026-10-08.json) contains
75 completed throughput records, eight whole-workload profiles, controls and
binary/source/prompt hashes, final correctness and API receipts, and rejected
or incomplete runs. This qualification covers the recorded GLM mixed/Q2 CUDA
workloads; it does not qualify other families, Metal or a new 1M Prefill path.
