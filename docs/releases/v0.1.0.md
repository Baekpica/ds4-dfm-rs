# v0.1.0: independent Rust-host baseline

Status: qualified on 2026-09-07 for the artifact and workload scope below.
`v0.1.0` identifies the merged release commit; the production implementation
matches the tested `9562f42` candidate. Final changes record this evidence
and shorten two test names without changing runtime behavior.

> The first independent Rust-host release with a stable host/runtime boundary
> and a native performance-observability workflow.

The RC series established migration, parity, and ownership. v0.1.0 makes the
independent Rust host the product: runtime, scheduling/policy, serving,
KV/state, distributed orchestration, observability, and performance control.
CUDA, MMQ, VMM, and hardware-specific kernels remain native compute.
The boundary follows the existing [architecture](../rust-migration/ARCHITECTURE.md)
and [opaque FFI contract](../rust-migration/FFI_CONTRACT.md).

`ds4-perf` is the first performance subsystem owned by this independent host.
It turns existing benchmark/profiler practice into a reproducible Rust workflow:

```text
ds4-bench -> ds4-perf scout -> nsys + NVTX -> diagnosis
          -> targeted ncu -> code change -> same-workload A/B + correctness proof
```

This is an initial stable baseline, not a claim that engine development is
finished. Stability requires both the host/runtime contract and the production
evidence; adding a profiler alone does not satisfy the release bar.

Scouting now reuses the successfully completed SQLite export for subsequent

compared three fresh processes per build, both without Nsight: median prefill
-0.13%, decode -0.44%, with exact frontier logits and eight greedy tokens.
That instrumentation result is separate from the RC.4 release comparison.
The RC.4 worker RSS comparison excludes device allocations. The newer matching
Qwen owner intentionally carries 278 aligned Q8 tensors / 3.62 GiB instead of
160 / 0.94 GiB. The release retains this existing +2.68 GiB D2R tradeoff
with its measured prefill gain and validated context scope. It is a disclosed
deviation from a no-resident-growth bar; lifecycle/cleanup PASS does not
assert unchanged resident memory.

## Qwen numerical qualification

RC.4 and candidate frontier logits repeat byte-for-byte within each version.
Across versions,
the 2K frontier argmax changes from 264 to 303 (top-10 overlap 10/10,
KL 0.057555, relative RMS 0.134996). Do not claim identical continuation or
attribute this difference to the KV parser/NVTX changes.

The [numerical contract](../prefill-decode-optimization-playbook.md#5-numerics-the-contract-per-class-of-change)
is per optimization class. Its class-5.3 band applies to each D2R change,
while QSA/GDN fp32 reorderings have component-reference and state self-parity
gates. Applying the D2R band to all post-RC.4 changes together would mix those
contracts. The fresh same-binary comparisons use baseline-to-candidate KL:

| D2R transition | Argmax | Top-10 overlap | KL | Relative RMS |
|---|---|---|---|---|
| Disabled -> K=2560 enabled | 303 -> 303 | 9/10 | 0.035529 | 0.109703 |
| K=2560 -> K=2560 plus K=6144 | 303 -> 303 | 10/10 | 0.047236 | 0.102946 |

All three configurations produce the same eight greedy IDs. The corresponding
K=2560/K=6144 F32-reference kernel tests pass. HC fusion and producer-Q8
kill switches each preserve the default frontier and eight IDs exactly.
The intermediate D2R configuration repeats byte-for-byte. Fresh GDN/QSA/HC
component tests pass; GDN output/reference max difference is 1.49e-8, with
exact chunk/decode self-parity. In a separate diagnostic build, reversing
`d8cc760` and disabling D2R/QSA/HC/Q8 changes reconstructs every RC.4 frontier
logit exactly. A Rust probe linked to the untouched RC.4 backend matches that
frontier and the control's eight IDs; the default candidate has a different,
repeatable continuation. The release retains the validated optimizations.

## Deferred to v0.1.x

`ds4-perf ncu`, `compare`, `regression`, and `tune`; a direct CUPTI collector;
automatic kernel tuning. These are follow-up candidates, not v0.1.0 blockers.
The first release only suggests bounded NCU commands and requires every code
change to return to the existing benchmark and correctness gates.
