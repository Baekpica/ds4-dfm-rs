# Gemma-4-26B-A4B device path, steps 1-8 (2026-11-02)

The CPU forward answers, at 1.26-1.33 s per token. This unit opens the device
path with the things that must be true before a token can run there: the whole
artifact resident, a row dot that agrees with the CPU oracle, a gather that
reads only the routed experts, a batched prefill on f16 tensor cores, the
layer's elementwise arithmetic, the rotary and attention kernels, and the
router's selection, and both ends of the tied embedding.

## What landed

- `native/gemma4/gemma4_gpu.h` and `native/gemma4/gemma4_gpu.cu`: map every
  RQVQ container the release names, check each header against the release's
  shape, upload every payload once with its own 256-byte-aligned slot and a
  zeroed 64-byte tail, and run one fused gather-and-dot per payload. The
  kernels are the VQ tools' own device code, ported for this payload:
  `gemv_v3blk` (block kernel, `/data/VQ_Tools/c/gpu/decode-gpu.cu:285-333`),
  `gemv_warp4` (dim-4 fast path, `:199-237`), `gemv_warp` (generic, `:619-656`),
  with `rd_idx_fmt` (`:110-133`) and the selection rule `v3_blk_ok` (`:66-68`).
- `crates/ds4-core/examples/gemma4_a4b_gpu_gate.rs`, behind the new
  `gemma4-gpu` feature: opens the release, lists every encoded container,
  prints the residency account, then gates two geometries against the CPU.
- `Makefile`: `tests/gemma4_gpu_gate`. The object is self-contained (no engine
  objects) and builds for this device (`-arch=native`) unless a `cuda-*`
  target has recorded an architecture.
- `gm4_gpu_rows` in the same header and module: the routed gather, one row
  list per call, every entry checked against the tensor's row count, gated
  against `Matrix::dot_rows` on both expert stacks.
- `gm4_gpu_prefill`, `gm4_gpu_prefill_rows` and `gm4_gpu_prefill_ready`: the
  tools' tiled f16 tensor-core prefill and its legacy fallback, gated against
  an f64 reference over activations rounded the way the mma rounds them.
- `gm4_gpu_rmsnorm`, `gm4_gpu_gelu_mul`, `gm4_gpu_residual_scale` and
  `gm4_gpu_softcap`: the layer's elementwise arithmetic, gated against the CPU
  forward's own functions.
- `gm4_gpu_rope` and `gm4_gpu_attention`: the two rotary flavours from the
  published table and one query token's attention over an f16 K/V history,
  gated against the forward's primitives and an f64 reference.
- `gm4_gpu_mul` and `gm4_gpu_router_topk`: the router's scale and its
  selection, gated so the eight chosen experts are the CPU's own indices.
- The two ends of the model needed no new kernel: the tied embedding is a
  one-row gather on the input side and the whole-container row kernel on the
  logits side, and both are measured with the softcap applied.

The third column is the independent reference: the whole tensor decoded to f32
and dotted in f64. It is reported because agreement between two f32 paths is
not proof. The device is the more accurate side on both tensors, as a 32-lane
partial sum should be; the CPU's error is the sequential sum's.

The two geometries are picked by the tools' rule, not by hand: `q_proj` is
nc 4096, so the 12-bit stream and `nidx_row 352` satisfy `v3_blk_ok` and the
block kernel runs; the router is nc 256, whose 8-bit stream fails that
precondition and takes the dim-4 fast path.

Timing is per stack, host-to-host through the ABI (x upload, launch, sync, y
download), and is not a token time. For scale, the VQ tools' own `decode-gpu
--check` on the same q_proj container measured the block kernel at 0.0342 ms
(130.9 GB/s) launch-only, so the ABI's transfers and one sync cost about 6 us
of the 40. That is the next unit's business, not this one's.

## Step 3: the routed gather

A mixture layer routes each token to eight of 128 experts. Its two stacks are
`experts.gate_up_proj` at 180224 x 2816 (128 x 1408 rows) and
`experts.down_proj` at 360448 x 704 (128 x 2816 rows), both dim 8 / nc 4096, so
both run the block kernel. On the CPU the forward already gathers:
`Matrix::dot_rows` names the rows an expert needs (`weights.rs:107-127`).

`gm4_gpu_rows` is the same kernel with a row list. A warp's row is `rl[lo]`
instead of `row0 + lo` (`gemma4_gpu.cu`, `row_of`), so the launch costs one
extra load per row, not per index. Every entry is checked against the tensor's
row count on the host before the list is uploaded, because a row past the end
would read the next payload's stream.

```
GATHER ...experts.gate_up_proj 180224x2816 rows 11264 of 180224
       experts [0, 3, 17, 42, 64, 91, 120, 127]
       cpu 7.1 ms gpu 0.755 ms relL2 9.768e-7 maxabs 7.153e-6 scale 3.603e0
  F64 cpu 9.683e-7 gpu 1.087e-7 over 11264 gathered rows
  MIX interleaved 128 rows + repeat: relL2 9.284e-7 maxabs 3.338e-6
       repeat bit-identical true
  REFUSE row 180224: row 180224 at entry 0 is outside the tensor's 180224 rows
  TIMING best 0.093 ms of 3 launches, 11.4 MiB of the stack read at 128.0 GB/s
GATHER ...experts.down_proj 360448x704 rows 22528 of 360448
       cpu 4.4 ms gpu 0.241 ms relL2 4.877e-7 maxabs 5.245e-6 scale 6.248e0
  F64 cpu 4.788e-7 gpu 9.172e-8 over 22528 gathered rows
  MIX interleaved 128 rows + repeat: relL2 5.135e-7 maxabs 1.371e-6
       repeat bit-identical true
  REFUSE row 360448: row 360448 at entry 0 is outside the tensor's 360448 rows
  TIMING best 0.083 ms of 3 launches, 5.8 MiB of the stack read at 73.3 GB/s
```

The routed shape reads 11.4 MiB of the 182.3 MiB gate/up stack and 5.8 MiB of
the 92.2 MiB down stack: 1/16 of the bytes, which is why one layer's experts
cost 0.18 ms of device time as against 0.9-1.0 ms for the whole stack. The
down gather runs at 73.3 GB/s against gate/up's 128.0 GB/s because its rows
carry 88 indices instead of 352, so the fixed per-row cost (index read, gain,
warp reduction) is a larger share.

Three checks beyond the eight-expert comparison:

- the f64 reference over the gathered rows is built from `Matrix::row`, the
  per-row decode path, not from the batched path the CPU oracle used;
- `MIX` interleaves the first and last expert in opposite directions and
  repeats a row, so a gather that quietly read a contiguous range from row 0
  would pass the shape check and fail here; the repeat must be bit-identical
  and is;
- a row equal to the row count must be refused, and the printed message is the
  refusal.

## Step 4: the tiled prefill

A prompt is processed as a batch, and a batch is where the artifact's decode
cost stops dominating: the weights are read once per tile and reused across
tokens. The VQ tools already have that kernel, and it is the one ported here
rather than a fresh design:

- `gemm_tiled_kernel` (`/data/VQ_Tools/c/gpu/decode-gpu.cu:376-518`) with its
  swizzle (`:349-353`), `ldmatrix` and `mma.sync.aligned.m16n8k16.row.col`
  (`:355-374`), the geometry gate `pre_ok` (`:536-541`), the shared-memory
  account (`:531-534`), the tile table (`:558-563`) and the launch dispatch
  (`:707-760`).
- `gemm_prefill_kernel` (`:588-612`), the legacy one-thread-per-(row, token)
  fallback the reference keeps for any geometry the tiled kernel cannot take.

The arithmetic decisions are the reference's, not this unit's: f16 rather than
bf16 because the codebook is f16 and bf16 would round every learned codeword
by 2^-8; a code word is copied into the tile with no conversion at all; and the
k16 loop restarts from zero and adds back with a plain FADD rather than letting
K accumulate inside the tensor core's own adder (`:337-341`).

The one thing the tiled path does cost is the activation rounding: x is f32 in
the model and f16 in the mma. The gate therefore has two references, and they
answer different questions:

```
PREFILL ...q_proj.weight 4096x2816 ntok 8 reference f64 over f16-round activations
  TILE bn 64 cb 0 relL2 2.449e-7 maxabs 1.866e-6 0.255 ms
  TILE bn 128 cb 0 relL2 2.449e-7 maxabs 1.866e-6 0.139 ms
    VSF32 relL2 1.818e-4 maxabs 1.266e-3 (the f16 input rounding; gate 2e-3)
    ONEHOT column 938 maxabs 0.000e0
    TIMING best 0.128 ms of 3 launches, 1443.5 GFLOP/s over the ideal count
  TILE bn 256 cb 0 relL2 2.449e-7 maxabs 1.866e-6 0.168 ms
  TILE bn 64 cb 1 relL2 2.449e-7 maxabs 1.866e-6 0.108 ms
  TILE bn 128 cb 1 relL2 2.449e-7 maxabs 1.866e-6 0.115 ms
  TILE bn 256 cb 1 REFUSED: a shared codebook with tile 256 needs 114688 bytes
       of shared memory, the device allows 101376
  BEST tile 64/1 at 0.108 ms, relL2 2.449e-7
```

At 64 tokens the same tensor takes 0.330-0.356 ms per tile shape against
2.7 ms for 64 serial GEMVs (0.042 ms each), so the tile is worth about 8x on a
real prompt, and the reported 4445.5 GFLOP/s counts only the ideal multiply
count, not the decode.

Three things the numbers prove:

- every tile shape lands on the same relL2 (2.449e-7 at 8 tokens, 2.488e-7 at
  64) against the f64 reference, so the tile geometry changes the schedule and
  not the arithmetic;
- the difference from the unrounded f32 path is 1.8e-4 relL2, which is the f16
  input rounding alone; the kernel's own error is the 2.5e-7 line;
- a one-hot column is reproduced with zero difference, because 1.0 is exact in
  f16 and the gain is applied after the mma in f32.

The fallback and the slice:

```
PREFILL ...router.proj.weight 128x2816 ntok 8 bn 0
    (legacy: dim 4 nc 256 does not fit the tiled kernel) relL2 9.598e-7
PREFILL_SLICE ...experts.gate_up_proj rows 0..128 of 180224 ntok 8
    relL2 2.535e-7 maxabs 1.052e-6 rows outside the slice untouched true
```

The router is the artifact's only dim-4, 8-bit-codebook matrix, and 8 bits
fails the 12-bit precondition of the tiled fill, so it takes the legacy kernel
and still matches the f64 reference at 9.6e-7. Its activations stay f32 there,
which is why that reference does not round them. The slice is a routed
expert's prefill: it writes the full-row layout `y[t * rows + r]` and leaves
every row outside the slice untouched, which the check reads back.

Two tile shapes are refused by this device rather than by the code: a shared
codebook with bn 256 needs 114,688 bytes against the 101,376-byte opt-in
window. That is the kind of fact the tuner exists to record.

## Step 5: the layer's elementwise arithmetic

There is no device reference for these four ops in the VQ tools, so the
reference is this repository's CPU forward, and the gate compares against the
forward's own functions instead of a second copy of the formula: `rms_norm`,
`gelu` and `bf16_round` are now published (`forward.rs:42-66`, re-exported from
`gemma4_a4b.rs`) precisely so a device kernel can be measured against the
function the CPU path actually runs.

- `rmsnorm_kernel`: `Gemma4RMSNorm.forward`, one block per row, tree-wise sum
  of squares, `rsqrtf(mean + eps)`, optional weight. Batched, because a
  prefill has one row per token and the attention head norms are 256 wide.
- `gelu_mul_kernel`: `gelu_pytorch_tanh` times a second vector, the form both
  feed-forwards write, with the forward's constants verbatim.
- `residual_scale_kernel`: `out = (x + add) * scale` with `add` optional, which
  is the residual add and the layer scalar the forward applies as two loops.
- `softcap_kernel`: `cap * tanh(y / cap)`, the last step before the logits
  leave the model.

```
ELEMENTWISE embed scale 53 (bf16 of sqrt(2816) = 53.065998)
RMSNORM weighted 4x2816 vs cpu 3.940e-7 (maxabs 1.192e-6) vs f64 4.442e-8
RMSNORM weightless 4x2816 vs cpu 4.013e-7 (maxabs 1.192e-6) vs f64 3.757e-8
RMSNORM weighted 2x256 vs cpu 4.577e-8 (maxabs 1.192e-7) vs f64 3.893e-8
RMSNORM weightless 2x256 vs cpu 5.372e-8 (maxabs 1.192e-7) vs f64 3.228e-8
GELU_MUL 2816 vs cpu 3.130e-9 (maxabs 2.384e-7) vs f64 3.590e-8
RESIDUAL_SCALE scale 1 bit-identical 0 differences of 2816
RESIDUAL_SCALE scale 1.7 bit-identical 0 differences of 2816
RESIDUAL_SCALE scale 53 bit-identical 0 differences of 2816
SOFTCAP 2816 cap 30 vs f64 4.367e-8 maxabs 3.788e-6
```

The norm is the one place where the device and the CPU legitimately differ in
the last bits: the block reduces the squares tree-wise, the CPU sums them in
order, so 3.9e-7 against the CPU and 4.4e-8 against f64 is the reduction order
and not a defect. The residual and the layer scalar are f32 arithmetic on both
sides and agree bit for bit at three scales; a nonzero count there would be a
different rounding, which is why the check is exact rather than a tolerance.

The embedding scale is printed because it is a constant that changes every
logit if it is taken at face value: the checkpoint is bf16, so
`embed_scale.to(dtype)` is `bf16(sqrt(2816))` = 53, not 53.0659
(`forward.rs:325-327`).

These entry points are host in, host out like the rest of the ABI, so the
numbers above include two copies each. The kernels are what the chain will
reuse; only the wrapper around them changes when the activations stay on the
device.

## Step 6: rotary and decode attention

The mechanism here had to be settled from the source before a kernel was
written, and the earlier unit's notes were not enough. `gemma.rs` in
/data/ds4-dfm-rs describes the same geometry, but that file is mid-unit and
was explicitly not counted as evidence. The source used instead is the
official implementation, checked out locally:

    /data/refs/transformers-5.14.1/transformers/models/gemma4/modeling_gemma4.py
    /data/refs/transformers-5.14.1/transformers/modeling_rope_utils.py
    /data/refs/transformers-5.14.1/transformers/masking_utils.py

Four facts came out of it, each cited in the kernel's header comment:

- `rotate_half` pairs `d` with `d + width/2` over the whole head width and the
  table is folded by `cat(freqs, freqs)` (`modeling_gemma4.py:786-814`), so a
  zero frequency is an exact identity pair.
- Proportional RoPE sets `rope_angles = int(partial * head_dim // 2)` and
  `inv[i] = 1/base^(2i/head_dim)` where the divisor is the **full head width**,
  not the rotated width, because the initializer is passed
  `head_dim_key="global_head_dim"` (`modeling_rope_utils.py:227-244` and
  `modeling_gemma4.py:1120-1124`). The first 64 of 256 pairs rotate on a full
  layer; the rest are zero.
- The attention block normalises q and k per head, normalises v with no
  weight, takes the value from the *raw* k projection when `k_eq_v` holds, and
  uses `scaling = 1.0` (`modeling_gemma4.py:1183-1296`, `:1200`).
- Softmax is upcast to fp32, and the sliding predicate is `kv > q - window`
  with the causal `kv <= q`, i.e. exactly `window` keys including the query
  (`modeling_gemma4.py:846`, `masking_utils.py:92-101`).

The CPU forward already agreed with all four; the unit turned them into the
published `Config::rope_inv` and the published `rope`/`normalize_heads`, so
both paths and the gate share one definition.

```
ROPE Sliding heads 16 width 256 pos 12345 rotated pairs 128 of 128
     relL2 4.720e-8 maxabs 4.768e-7
ROPE Full heads 16 width 512 pos 12345 rotated pairs 64 of 256
     relL2 2.093e-8 maxabs 2.384e-7
ATTENTION layer 0 Sliding heads 16 kv 8 width 256 positions 1300 window 1024
     first 276: vs cpu 3.135e-4 (maxabs 1.715e-3) vs f64(f16 kv) 3.366e-7
  WINDOW a wider window changes the output by relL2 3.300e-3
ATTENTION layer 5 Full heads 16 kv 2 width 512 positions 192 window all
     first 0: vs cpu 2.297e-4 (maxabs 9.568e-4) vs f64(f16 kv) 1.129e-7
```

The kernel is one block per head: a warp takes every nwarps-th position for
the score pass, the block shares an fp32 softmax, and the value pass is one
thread per dimension with no reduction. The sliding case clips to the last
1024 of 1300 positions, and the check that a wider window moves the output by
3.3e-3 is what proves the mask is applied rather than the whole history.

Two numbers differ from the CPU on purpose. The 2-3e-4 line is the f16 KV
cache against the CPU's f32 KV, which is the cache's stated cost and is finer
than the reference's bf16 activations; the 1.1-3.4e-7 line against the f64
reference over the same f16 values is the kernel's own error.

One difference from the reference to remember for any future torch comparison:
`modeling_gemma4.py:1177` returns cos/sin cast to the activation dtype, so the
reference rotates with bf16 tables. This path keeps them f32, like the CPU
forward, so a torch logits diff would carry that rounding.

## Step 7: the router's selection

The router is the one place where a small numeric difference can change the
answer, because the experts it picks are discrete: a 1e-7 difference in two
competing probabilities either leaves the top-8 alone or swaps an expert and
changes the layer's output. So the gate compares the *indices* exactly and the
arithmetic only as context.

The chain is the forward's (`forward.rs:365-381`): a weightless RMSNorm, a
per-dimension multiply by `router.scale / sqrt(hidden)`, the 128-way dim-4
projection that already has a gated kernel, then `softmax` -> `top_k` ->
renormalise -> per-expert scale. `softmax` and `top_k` are now published from
the forward too, so the tie rule (highest first, ties to the lower index) has
one definition.

```
ROUTER layer 0 experts 128 top 8: scores relL2 9.368e-7 probs relL2 6.598e-7
       weights relL2 6.921e-7 maxabs 1.341e-7
  PICKED cpu    [88, 42, 122, 105, 63, 112, 41, 74]
  PICKED device [88, 42, 122, 105, 63, 112, 41, 74] identical true
  WEIGHTS without per-expert scale sum to 0.9999999 (expected 1)
```

The selection kernel is one block with a thread per expert for the softmax and
a single thread for the k passes, which keeps the tie rule readable and costs
128 comparisons per slot at most. The last line checks the other branch: with
no per-expert scale the weights are the renormalised probabilities, so they
must sum to one.

## Step 8: the two ends, and the largest read

The embeddings are tied, so the same 262144 x 2816 container is both the
input lookup and the logits head. No new kernel was needed for either: the
input end is the gather of one row, and the head is the whole-tensor row
kernel from step 2. The unit is the measurement and the checks.

```
EMBED ...embed_tokens.weight token 12345 of 262144x2816: one-hot column 938
      device -0.023857117 decoded -0.023857117 maxabs 0.000e0, forward scale 53
HEAD ...embed_tokens.weight 262144x2816 threads 128: cpu 129.6 ms
      gpu best-of-3 1.590 ms relL2 9.958e-7 maxabs 8.583e-6 174.8 GB/s
HEAD ... threads 256: cpu 129.6 ms gpu best-of-3 1.520 ms relL2 9.958e-7
      182.9 GB/s
HEAD ... threads 512: cpu 129.6 ms gpu best-of-3 1.532 ms relL2 9.958e-7
      181.5 GB/s
  BEST threads 256 at 1.520 ms
  SOFTCAP cap 30 applied to 262144 logits: relL2 4.649e-8 maxabs 4.862e-7
```

The head is 278 MB of payload, the largest single read a token makes, and it
costs 1.5 ms at 183 GB/s: 75x the CPU's 115-130 ms and, at this geometry, the
floor for one token's logits. The first run of this check reported a different
winner because each thread count was a single launch; the numbers above are
best-of-three after a warm-up, and two such runs agree to 0.5%. 128 threads is
about 4% behind 256 and 512, which are within noise of each other — the
tuner's earlier record of 179.3 GB/s at 512 threads is the same fact.

The input end is a one-hot gather, which must be exact: the device returns
-0.023857117 for the column the decoded row holds, with zero difference.

## The finding: the CPU oracle halved every subnormal half

The first gate run failed at 4.5e-5 relL2, with the CPU the accurate side
(9.2e-7 from f64) and the device 4.5e-5. A one-hot probe isolated it: with one
activation column, a row's dot is a single stored value, and it still differed
by 2.6e-5.

Hand-decoding the payload settled it. Row 1429, column 0 of `q_proj`:

```
stage 0  index 383   codebook 5.155801773071289e-05   gain 1.0
stage 1  index 4077  codebook 0.0035457611083984375   gain 1.0
sum      0.0035973191261291504   <- the device's value
```

5.1558e-05 is a subnormal half. `crates/ds4-core/src/vq.rs`'s `f16_to_f32`
normalized subnormals starting from exponent field 112 instead of 113, which
halves every subnormal codeword. The reference is the producer's decoder,
`/data/VQ_Tools/crates/vq-format/src/lib.rs:86-108`, which starts at 113; the
C function the comment cited (`ds41_vq_fmt.h:37-43`, `ds4vq_f16`) carries the
same off-by-one, and the Rust port inherited it.

Fixed in the family's decoder, with a regression test
(`tests/vq.rs::half_subnormals_are_exact`). After the fix the gates read as
above, every one-hot probe is exact, and the CPU forward still answers
"Stockholm".

The C `ds4vq_f16` in `ds41_vq_fmt.h` was not changed: it is the native
engine's decoder for the older VQ families, and correcting it would move their
recorded numbers. It is reported here so it can be its own unit, with its own
re-measurement, on the family it touches.

## Limits this unit leaves in place

- One host round trip per call: no device-resident activation buffer, no
  chained launches, one sync and one row-list upload per gather. The prefill
  takes transposed host activations and returns a host [ntok][rows] block, so
  a real prompt chunk would copy twice; the model step needs the chain, with
  the row list and the activations written on the device.
- No serving integration and no KV ring
  yet: attention runs against an explicit history passed in per call. The
  residency is all-or-nothing (9.0 GB), and the card has 1.5 GiB left at the
  measured moment: KV, workspace, prefill tiles and logits must fit in that.
- The kernels read the tools' DQV3 only. The engine's DQV3 (32-byte header,
  `cb_off`, fixed 12 bits) is refused by the payload check, as it is on the
  Rust side.

## Reproduce

```
make tests/gemma4_gpu_gate
./tests/gemma4_gpu_gate --dir /data/vq-artifacts/gemma-4-26b-a4b-8x4096 \
    --timing 5 --onehot 0,33,351
```

nvcc is at `/usr/local/cuda/bin` and not on `PATH`; the Makefile uses
`$(CUDA_HOME)/bin/nvcc` directly. `/tmp` is a full 16 GB tmpfs on this host, so
builds need `TMPDIR` pointed at a real filesystem (`/data/tmp/build-tmp`).
