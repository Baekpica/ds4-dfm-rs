# Gemma-4-26B-A4B device path, steps 1-9c (2026-11-02)

The CPU forward answers, at 1.26-1.33 s per token. This unit opens the device
path with the things that must be true before a token can run there: the whole
artifact resident, a row dot that agrees with the CPU oracle, a gather that
reads only the routed experts, a batched prefill on f16 tensor cores, the
layer's elementwise arithmetic, the rotary and attention kernels, the router's
selection, both ends of the tied embedding, the per-layer KV cache that lets
attention read a history the device keeps, one whole layer chained on the
device, and that chain priced per section so the remaining cost has a name.

## What landed

- `native/gemma4/gemma4_gpu.h` and `native/gemma4/gemma4_gpu.cu`: map every
  RQVQ container the release names, check each header against the release's
  shape, upload every payload once with its own 256-byte-aligned slot and a
  zeroed 64-byte tail, and run one fused gather-and-dot per payload. The
  kernels are the VQ tools' own device code, ported for this payload:
  `gemv_v3blk` (block kernel, `/data/VQ_tools/c/gpu/decode-gpu.cu:285-333`),
  `gemv_warp4` (dim-4 fast path, `:199-237`), `gemv_warp` (generic, `:619-656`),
  with `rd_idx_fmt` (`:110-133`) and the selection rule `v3_blk_ok` (`:66-68`).
- `crates/ds4-core/examples/gemma4_a4b_gpu_gate.rs`, behind the new
  `gemma4-gpu` feature: opens the release, lists every encoded container,
  prints the residency account, then gates two geometries against the CPU.
- `Makefile`: `tests/gemma4_gpu_gate`. The object is self-contained (no engine
  objects) and builds for this device (`-arch=native`) unless a `cuda-*`
  target has recorded an architecture.
- `gm4_gpu_rows` in the same header and module: the routed gather, one row
  list per call, every entry checked against the tensor's row count, gated
  against `Matrix::dot_rows` on both expert stacks.
- `gm4_gpu_prefill`, `gm4_gpu_prefill_rows` and `gm4_gpu_prefill_ready`: the
  tools' tiled f16 tensor-core prefill and its legacy fallback, gated against
  an f64 reference over activations rounded the way the mma rounds them.
- `gm4_gpu_rmsnorm`, `gm4_gpu_gelu_mul`, `gm4_gpu_residual_scale` and
  `gm4_gpu_softcap`: the layer's elementwise arithmetic, gated against the CPU
  forward's own functions.
- `gm4_gpu_rope` and `gm4_gpu_attention`: the two rotary flavours from the
  published table and one query token's attention over an f16 K/V history,
  gated against the forward's primitives and an f64 reference.
- `gm4_gpu_mul` and `gm4_gpu_router_topk`: the router's scale and its
  selection, gated so the eight chosen experts are the CPU's own indices.
- The two ends of the model needed no new kernel: the tied embedding is a
  one-row gather on the input side and the whole-container row kernel on the
  logits side, and both are measured with the softcap applied.
- `gm4_gpu_kv_new`, `gm4_gpu_kv_put`, `gm4_gpu_kv_get`, `gm4_gpu_kv_reset`,
  `gm4_gpu_kv_free` and `gm4_gpu_attention_ring`: one layer's f16 key/value
  cache on the device, the structure and the slot rule of the CPU session's
  `Kv` (`forward.rs:239-269`), with attention reading the cache instead of a
  host history. `attn_decode_kernel` grew a slot function, so the dense path
  and the ring are the same kernel and the same arithmetic.
- `gm4_gpu_layer_new`, `gm4_gpu_layer_forward` and `gm4_gpu_layer_free`: one
  layer wired end to end on the device, with one arena for every intermediate,
  one upload and one download per step, and no sync between its launches. The
  router's picks stay in device memory: a new `rowlist_kernel` expands them
  into the expert row lists and a new `axpy_kernel` accumulates each expert's
  down projection with its weight. `Session::layer_at` publishes the CPU's own
  layer for the gate, so the reference is the forward, not a copy of it.
- `gm4_gpu_layer_timing` and `gm4_gpu_layer_sections`: nine event boundaries in
  the chain, opt-in, so a per-layer total can be read as the sections that make
  it. Nothing about the launches changes when they are on.
- `attn_split_kernel` and `attn_combine_kernel`: decode attention in the
  flash-decoding shape, one block per (head, run of the window), replacing the
  one-block-per-head kernel. The ring gate's bit-identity between the dense and
  ring walks is preserved because the run schedule depends only on the head
  count and the window.
- `router_topk_kernel` selects with k rounds of a 32-lane argmax: one warp,
  one strided slice per lane, the CPU's tie rule as the compare.
- `gelu_mul_blocks_kernel`, `moe_reduce_kernel` and `Layout.xrows`/`xcols`:
  one blocked gelu, one down gather over the concatenation of the k expert
  blocks with each block's own activation, and one weighted reduce - the
  reference engine's reduce shape (`ds41_vq_decode.cuh:179-185`).

(130.9 GB/s) launch-only, so the ABI's transfers and one sync cost about 6 us
of the 40. That is the next unit's business, not this one's.

## Step 3: the routed gather

A mixture layer routes each token to eight of 128 experts. Its two stacks are
`experts.gate_up_proj` at 180224 x 2816 (128 x 1408 rows) and
`experts.down_proj` at 360448 x 704 (128 x 2816 rows), both dim 8 / nc 4096, so
both run the block kernel. On the CPU the forward already gathers:
`Matrix::dot_rows` names the rows an expert needs (`weights.rs:107-127`).

`gm4_gpu_rows` is the same kernel with a row list. A warp's row is `rl[lo]`
instead of `row0 + lo` (`gemma4_gpu.cu`, `row_of`), so the launch costs one
extra load per row, not per index. Every entry is checked against the tensor's
row count on the host before the list is uploaded, because a row past the end
would read the next payload's stream.

```
GATHER ...experts.gate_up_proj 180224x2816 rows 11264 of 180224
       experts [0, 3, 17, 42, 64, 91, 120, 127]
       cpu 7.1 ms gpu 0.755 ms relL2 9.768e-7 maxabs 7.153e-6 scale 3.603e0
  F64 cpu 9.683e-7 gpu 1.087e-7 over 11264 gathered rows
  MIX interleaved 128 rows + repeat: relL2 9.284e-7 maxabs 3.338e-6
       repeat bit-identical true
  REFUSE row 180224: row 180224 at entry 0 is outside the tensor's 180224 rows
  TIMING best 0.093 ms of 3 launches, 11.4 MiB of the stack read at 128.0 GB/s
GATHER ...experts.down_proj 360448x704 rows 22528 of 360448
       cpu 4.4 ms gpu 0.241 ms relL2 4.877e-7 maxabs 5.245e-6 scale 6.248e0
  F64 cpu 4.788e-7 gpu 9.172e-8 over 22528 gathered rows
  MIX interleaved 128 rows + repeat: relL2 5.135e-7 maxabs 1.371e-6
       repeat bit-identical true
  REFUSE row 360448: row 360448 at entry 0 is outside the tensor's 360448 rows
  TIMING best 0.083 ms of 3 launches, 5.8 MiB of the stack read at 73.3 GB/s
```

The routed shape reads 11.4 MiB of the 182.3 MiB gate/up stack and 5.8 MiB of
the 92.2 MiB down stack: 1/16 of the bytes, which is why one layer's experts
cost 0.18 ms of device time as against 0.9-1.0 ms for the whole stack. The
down gather runs at 73.3 GB/s against gate/up's 128.0 GB/s because its rows
carry 88 indices instead of 352, so the fixed per-row cost (index read, gain,
warp reduction) is a larger share.

Three checks beyond the eight-expert comparison:

- the f64 reference over the gathered rows is built from `Matrix::row`, the
  per-row decode path, not from the batched path the CPU oracle used;
- `MIX` interleaves the first and last expert in opposite directions and
  repeats a row, so a gather that quietly read a contiguous range from row 0
  would pass the shape check and fail here; the repeat must be bit-identical
  and is;
- a row equal to the row count must be refused, and the printed message is the
  refusal.

## Step 4: the tiled prefill

A prompt is processed as a batch, and a batch is where the artifact's decode
cost stops dominating: the weights are read once per tile and reused across
tokens. The VQ tools already have that kernel, and it is the one ported here
rather than a fresh design:

- `gemm_tiled_kernel` (`/data/VQ_tools/c/gpu/decode-gpu.cu:376-518`) with its
  swizzle (`:349-353`), `ldmatrix` and `mma.sync.aligned.m16n8k16.row.col`
  (`:355-374`), the geometry gate `pre_ok` (`:536-541`), the shared-memory
  account (`:531-534`), the tile table (`:558-563`) and the launch dispatch
  (`:707-760`).
- `gemm_prefill_kernel` (`:588-612`), the legacy one-thread-per-(row, token)
  fallback the reference keeps for any geometry the tiled kernel cannot take.

The arithmetic decisions are the reference's, not this unit's: f16 rather than
bf16 because the codebook is f16 and bf16 would round every learned codeword
by 2^-8; a code word is copied into the tile with no conversion at all; and the
k16 loop restarts from zero and adds back with a plain FADD rather than letting
K accumulate inside the tensor core's own adder (`:337-341`).

The one thing the tiled path does cost is the activation rounding: x is f32 in
the model and f16 in the mma. The gate therefore has two references, and they
answer different questions:

```
PREFILL ...q_proj.weight 4096x2816 ntok 8 reference f64 over f16-round activations
  TILE bn 64 cb 0 relL2 2.449e-7 maxabs 1.866e-6 0.255 ms
  TILE bn 128 cb 0 relL2 2.449e-7 maxabs 1.866e-6 0.139 ms
    VSF32 relL2 1.818e-4 maxabs 1.266e-3 (the f16 input rounding; gate 2e-3)
    ONEHOT column 938 maxabs 0.000e0
    TIMING best 0.128 ms of 3 launches, 1443.5 GFLOP/s over the ideal count
  TILE bn 256 cb 0 relL2 2.449e-7 maxabs 1.866e-6 0.168 ms
  TILE bn 64 cb 1 relL2 2.449e-7 maxabs 1.866e-6 0.108 ms
  TILE bn 128 cb 1 relL2 2.449e-7 maxabs 1.866e-6 0.115 ms
  TILE bn 256 cb 1 REFUSED: a shared codebook with tile 256 needs 114688 bytes
       of shared memory, the device allows 101376
  BEST tile 64/1 at 0.108 ms, relL2 2.449e-7
```

At 64 tokens the same tensor takes 0.330-0.356 ms per tile shape against
2.7 ms for 64 serial GEMVs (0.042 ms each), so the tile is worth about 8x on a
real prompt, and the reported 4445.5 GFLOP/s counts only the ideal multiply
count, not the decode.

Three things the numbers prove:

- every tile shape lands on the same relL2 (2.449e-7 at 8 tokens, 2.488e-7 at
  64) against the f64 reference, so the tile geometry changes the schedule and
  not the arithmetic;
- the difference from the unrounded f32 path is 1.8e-4 relL2, which is the f16
  input rounding alone; the kernel's own error is the 2.5e-7 line;
- a one-hot column is reproduced with zero difference, because 1.0 is exact in
  f16 and the gain is applied after the mma in f32.

The fallback and the slice:

```
PREFILL ...router.proj.weight 128x2816 ntok 8 bn 0
    (legacy: dim 4 nc 256 does not fit the tiled kernel) relL2 9.598e-7
PREFILL_SLICE ...experts.gate_up_proj rows 0..128 of 180224 ntok 8
    relL2 2.535e-7 maxabs 1.052e-6 rows outside the slice untouched true
```

The router is the artifact's only dim-4, 8-bit-codebook matrix, and 8 bits
fails the 12-bit precondition of the tiled fill, so it takes the legacy kernel
and still matches the f64 reference at 9.6e-7. Its activations stay f32 there,
which is why that reference does not round them. The slice is a routed
expert's prefill: it writes the full-row layout `y[t * rows + r]` and leaves
every row outside the slice untouched, which the check reads back.

Two tile shapes are refused by this device rather than by the code: a shared
codebook with bn 256 needs 114,688 bytes against the 101,376-byte opt-in
window. That is the kind of fact the tuner exists to record.

## Step 5: the layer's elementwise arithmetic

There is no device reference for these four ops in the VQ tools, so the
reference is this repository's CPU forward, and the gate compares against the
forward's own functions instead of a second copy of the formula: `rms_norm`,
`gelu` and `bf16_round` are now published (`forward.rs:42-66`, re-exported from
`gemma4_a4b.rs`) precisely so a device kernel can be measured against the
function the CPU path actually runs.

- `rmsnorm_kernel`: `Gemma4RMSNorm.forward`, one block per row, tree-wise sum
  of squares, `rsqrtf(mean + eps)`, optional weight. Batched, because a
  prefill has one row per token and the attention head norms are 256 wide.
- `gelu_mul_kernel`: `gelu_pytorch_tanh` times a second vector, the form both
  feed-forwards write, with the forward's constants verbatim.
- `residual_scale_kernel`: `out = (x + add) * scale` with `add` optional, which
  is the residual add and the layer scalar the forward applies as two loops.
- `softcap_kernel`: `cap * tanh(y / cap)`, the last step before the logits
  leave the model.

```
ELEMENTWISE embed scale 53 (bf16 of sqrt(2816) = 53.065998)
RMSNORM weighted 4x2816 vs cpu 3.940e-7 (maxabs 1.192e-6) vs f64 4.442e-8
RMSNORM weightless 4x2816 vs cpu 4.013e-7 (maxabs 1.192e-6) vs f64 3.757e-8
RMSNORM weighted 2x256 vs cpu 4.577e-8 (maxabs 1.192e-7) vs f64 3.893e-8
RMSNORM weightless 2x256 vs cpu 5.372e-8 (maxabs 1.192e-7) vs f64 3.228e-8
GELU_MUL 2816 vs cpu 3.130e-9 (maxabs 2.384e-7) vs f64 3.590e-8
RESIDUAL_SCALE scale 1 bit-identical 0 differences of 2816
RESIDUAL_SCALE scale 1.7 bit-identical 0 differences of 2816
RESIDUAL_SCALE scale 53 bit-identical 0 differences of 2816
SOFTCAP 2816 cap 30 vs f64 4.367e-8 maxabs 3.788e-6
```

The norm is the one place where the device and the CPU legitimately differ in
the last bits: the block reduces the squares tree-wise, the CPU sums them in
order, so 3.9e-7 against the CPU and 4.4e-8 against f64 is the reduction order
and not a defect. The residual and the layer scalar are f32 arithmetic on both
sides and agree bit for bit at three scales; a nonzero count there would be a
different rounding, which is why the check is exact rather than a tolerance.

The embedding scale is printed because it is a constant that changes every
logit if it is taken at face value: the checkpoint is bf16, so
`embed_scale.to(dtype)` is `bf16(sqrt(2816))` = 53, not 53.0659
(`forward.rs:325-327`).

These entry points are host in, host out like the rest of the ABI, so the
numbers above include two copies each. The kernels are what the chain will
reuse; only the wrapper around them changes when the activations stay on the
device.

## Step 6: rotary and decode attention

The mechanism here had to be settled from the source before a kernel was
written, and the earlier unit's notes were not enough. `gemma.rs` in
/data/ds4-dfm-rs describes the same geometry, but that file is mid-unit and
was explicitly not counted as evidence. The source used instead is the
official implementation, checked out locally:

    /data/refs/transformers-5.14.1/transformers/models/gemma4/modeling_gemma4.py
    /data/refs/transformers-5.14.1/transformers/modeling_rope_utils.py
    /data/refs/transformers-5.14.1/transformers/masking_utils.py

Four facts came out of it, each cited in the kernel's header comment:

- `rotate_half` pairs `d` with `d + width/2` over the whole head width and the
  table is folded by `cat(freqs, freqs)` (`modeling_gemma4.py:786-814`), so a
  zero frequency is an exact identity pair.
- Proportional RoPE sets `rope_angles = int(partial * head_dim // 2)` and
  `inv[i] = 1/base^(2i/head_dim)` where the divisor is the **full head width**,
  not the rotated width, because the initializer is passed
  `head_dim_key="global_head_dim"` (`modeling_rope_utils.py:227-244` and
  `modeling_gemma4.py:1120-1124`). The first 64 of 256 pairs rotate on a full
  layer; the rest are zero.
- The attention block normalises q and k per head, normalises v with no
  weight, takes the value from the *raw* k projection when `k_eq_v` holds, and
  uses `scaling = 1.0` (`modeling_gemma4.py:1183-1296`, `:1200`).
- Softmax is upcast to fp32, and the sliding predicate is `kv > q - window`
  with the causal `kv <= q`, i.e. exactly `window` keys including the query
  (`modeling_gemma4.py:846`, `masking_utils.py:92-101`).

The CPU forward already agreed with all four; the unit turned them into the
published `Config::rope_inv` and the published `rope`/`normalize_heads`, so
both paths and the gate share one definition.

```
ROPE Sliding heads 16 width 256 pos 12345 rotated pairs 128 of 128
     relL2 4.720e-8 maxabs 4.768e-7
ROPE Full heads 16 width 512 pos 12345 rotated pairs 64 of 256
     relL2 2.093e-8 maxabs 2.384e-7
ATTENTION layer 0 Sliding heads 16 kv 8 width 256 positions 1300 window 1024
     first 276: vs cpu 3.135e-4 (maxabs 1.715e-3) vs f64(f16 kv) 3.366e-7
  WINDOW a wider window changes the output by relL2 3.300e-3
ATTENTION layer 5 Full heads 16 kv 2 width 512 positions 192 window all
     first 0: vs cpu 2.297e-4 (maxabs 9.568e-4) vs f64(f16 kv) 1.129e-7
```

The kernel is one block per head: a warp takes every nwarps-th position for
the score pass, the block shares an fp32 softmax, and the value pass is one
thread per dimension with no reduction. The sliding case clips to the last
1024 of 1300 positions, and the check that a wider window moves the output by
3.3e-3 is what proves the mask is applied rather than the whole history.

Two numbers differ from the CPU on purpose. The 2-3e-4 line is the f16 KV
cache against the CPU's f32 KV, which is the cache's stated cost and is finer
than the reference's bf16 activations; the 1.1-3.4e-7 line against the f64
reference over the same f16 values is the kernel's own error.

One difference from the reference to remember for any future torch comparison:
`modeling_gemma4.py:1177` returns cos/sin cast to the activation dtype, so the
reference rotates with bf16 tables. This path keeps them f32, like the CPU
forward, so a torch logits diff would carry that rounding.

## Step 7: the router's selection

The router is the one place where a small numeric difference can change the
answer, because the experts it picks are discrete: a 1e-7 difference in two
competing probabilities either leaves the top-8 alone or swaps an expert and
changes the layer's output. So the gate compares the *indices* exactly and the
arithmetic only as context.

The chain is the forward's (`forward.rs:365-381`): a weightless RMSNorm, a
per-dimension multiply by `router.scale / sqrt(hidden)`, the 128-way dim-4
projection that already has a gated kernel, then `softmax` -> `top_k` ->
renormalise -> per-expert scale. `softmax` and `top_k` are now published from
the forward too, so the tie rule (highest first, ties to the lower index) has
one definition.

```
ROUTER layer 0 experts 128 top 8: scores relL2 9.368e-7 probs relL2 6.598e-7
       weights relL2 6.921e-7 maxabs 1.341e-7
  PICKED cpu    [88, 42, 122, 105, 63, 112, 41, 74]
  PICKED device [88, 42, 122, 105, 63, 112, 41, 74] identical true
  WEIGHTS without per-expert scale sum to 0.9999999 (expected 1)
```

The selection kernel is one block with a thread per expert for the softmax and
a single thread for the k passes, which keeps the tie rule readable and costs
128 comparisons per slot at most. The last line checks the other branch: with
no per-expert scale the weights are the renormalised probabilities, so they
must sum to one.

## Step 8: the two ends, and the largest read

The embeddings are tied, so the same 262144 x 2816 container is both the
input lookup and the logits head. No new kernel was needed for either: the
input end is the gather of one row, and the head is the whole-tensor row
kernel from step 2. The unit is the measurement and the checks.

```
EMBED ...embed_tokens.weight token 12345 of 262144x2816: one-hot column 938
      device -0.023857117 decoded -0.023857117 maxabs 0.000e0, forward scale 53
HEAD ...embed_tokens.weight 262144x2816 threads 128: cpu 129.6 ms
      gpu best-of-3 1.590 ms relL2 9.958e-7 maxabs 8.583e-6 174.8 GB/s
HEAD ... threads 256: cpu 129.6 ms gpu best-of-3 1.520 ms relL2 9.958e-7
      182.9 GB/s
HEAD ... threads 512: cpu 129.6 ms gpu best-of-3 1.532 ms relL2 9.958e-7
      181.5 GB/s
  BEST threads 256 at 1.520 ms
  SOFTCAP cap 30 applied to 262144 logits: relL2 4.649e-8 maxabs 4.862e-7
```

The head is 278 MB of payload, the largest single read a token makes, and it
costs 1.5 ms at 183 GB/s: 75x the CPU's 115-130 ms and, at this geometry, the
floor for one token's logits. The first run of this check reported a different
winner because each thread count was a single launch; the numbers above are
best-of-three after a warm-up. The spread is not as tight as one run suggests:
two isolated runs agreed to 0.5% (1.52 ms), and a later run inside the whole
gate, with the prefill buffers allocated, reported 1.68 ms as its best. So the
honest reading is that 256 and 512 threads are not separable at this size and
that the cost is 1.5-1.7 ms depending on context; the tuner's earlier record of
179.3 GB/s at 512 threads is the same fact measured another way.

The input end is a one-hot gather, which must be exact: the device returns
-0.023857117 for the column the decoded row holds, with zero difference.

## Step 9a: the per-layer KV cache

Step 6's attention took a history from the host, which means one 4-8 KB K/V
upload per layer per token and a host copy of every layer's cache. The session
cannot be built that way. This step moves the cache itself to the device.

The object is the CPU session's own `Kv` (`forward.rs:239-269`), not a new
design: `per = kv_heads * head_dim` f16 values per position, `cap` positions,
and `slot(pos) = pos % cap` for a rolling layer or `pos` for a growing one. A
sliding layer is created with `window` = the layer's `config.sliding_window`,
so the ring holds exactly the window; a full layer is created appending, with
the session bound the caller names, because the CPU grows that cache lazily
(the checkpoint's 262,144 positions would be 5 GB). `attn_decode_kernel` now
maps every position through `kv_slot(p, cap, ring)`; the walk is still in
position order, so the ring changes addresses and never arithmetic.

Three claims, each with its own check, because a ring can be wrong in three
places: the cell it writes to, the cell it overwrites, and the attention that
reads it. Layer 0 is driven 276 positions past its window, which is the case
the dense gate could never exercise.

```
RESET layer 0 position 0 after a write and a reset: zeros true
RING SLOT layer 0 Sliding cap 1024 positions 1300 read back 276..1299
          maxabs 0.000e0
  WRAP position 0 and 1024 share slot 0: maxabs 0.000e0;
       position 0's own values are gone by 5.208e0
RING ATTENTION layer 0 Sliding from the cache at 1299, window 1024,
       vs f64(f16 kv) 3.366e-7 (maxabs 9.530e-7)
  DENSE the step-6 walk on the same history: relL2 0.000e0 maxabs 0.000e0
  TIMING one token's cache: put 0.009 ms, attention 0.239 ms at 1300 positions
RING SLOT layer 5 Full cap 4096 positions 192 read back 0..191 maxabs 0.000e0
RING ATTENTION layer 5 Full from the cache at 191, window all,
       vs f64(f16 kv) 1.129e-7 (maxabs 4.626e-7)
  DENSE the step-6 walk on the same history: relL2 0.000e0 maxabs 0.000e0
  TIMING one token's cache: put 0.009 ms, attention 0.097 ms at 192 positions
RING ACCOUNT 25 rings of 1024 and 5 appending caches of 4096: 280.0 MiB total,
       of which 80.0 MiB is the appending caches, so each doubling of the
       bound adds 80.0 MiB
```

The readback is exact, not close: a position's slot returns the f16 key and
value that were put there, and after the wrap position 0 and position 1024
return the same slot contents while position 0's own key and value are gone.
The attention from the cache reproduces step 6's number against the same f64
reference (3.366e-7 sliding, 1.129e-7 full) and is bit-identical to the dense
walk over the same history. That last zero is the point: the ring is a
permutation of addresses, and if it were anything else the difference would
show as soon as the window filled.

The cost is 280 MiB for the whole session's cache at a 4096-position bound,
0.239 ms of attention per token on the sliding layers and 0.009 ms to write a
position. Against the tools' measured 10.97 ms per routed token that is about
2%, and it fits: the residency leaves 1.5 GiB, of which the cache takes 280
MiB. Raising the full layers' bound to the checkpoint's 262,144 positions would
cost 5 GiB and does not fit, which is why the bound is the caller's.

## Step 9b: one layer, chained

The kernels were all gated by step 9a but nothing ran them in order: each entry
point uploaded its inputs and synced before returning, so a layer's chain was
fourteen round trips through the host and a host copy of every intermediate.
This step is the chain.

`gm4_gpu_layer_forward` runs the CPU layer in its own order
(`forward.rs:335-398`): the input norm, q/k/v, the per-head norms and rotary,
the cache write and the attention, then the `o_proj` that ends the CPU's
attention (`:462`), the post-attention norm and residual, the dense
feed-forward, the router and its top-k, the routed experts, and the two norms
and the scalar that close the layer. The only host traffic is the activation
uploaded at the start and the layer output downloaded at the end. The picks
stay on the device: `rowlist_kernel` turns the router's k indices into the
expert row lists (`expert * stride + r`, the CPU's own formula at
`forward.rs:377-383`) and `axpy_kernel` accumulates each expert with its
weight, so the selection never travels to the host and back.

The reference is the forward's own layer. `Session::layer_at` was added for
this, a three-line publication of the code `step` already runs, so the gate
compares against the forward rather than a second implementation of it.

```
LAYER 0 Sliding at 0: vs the forward's own layer relL2 1.510e-4 ...
  STAGE qb relL2 9.566e-7 | vb 9.455e-7 | o_proj(f16 v) 4.996e-6 | xb 1.052e-4
LAYER 0 Sliding at 24: relL2 2.408e-4
LAYER 5 Full at 0: relL2 5.655e-5
  STAGE qb relL2 9.717e-7 | vb 1.041e-6 | o_proj(f16 v) 5.494e-5 | xb 1.248e-4
LAYER 5 Full at 24: relL2 9.057e-5
  TIMING layer 0 Sliding 0.566 ms | layer 5 Full 0.682 ms
LAYER PROJECTION 25 x 0.566 ms + 5 x 0.682 ms = 17.56 ms per token,
       57.0 tok/s, against the 10.97 ms the tools measured for the routed
       weight stream
```

The stage lines are what make the output number readable. At position 0 there
is one key, so the softmax is 1 and the attention core is the value head
itself; the gate recomputes each stage with the forward's own primitives and
compares it against a probe of the device arena. qb and vb are 1e-6, the
`o_proj` of the f16-rounded value head is 5e-6 to 5e-5, and the layer's output
is 1.5e-4. That last number is the cache, not the chain: the key and value are
f16 from the first position, which is the format step 9a measured at 3.1e-4
against the CPU's f32 history over 1300 positions. The runner-up at 24
positions is 2.4e-4 for the same reason. This is why the bands are 1e-3 and
2e-3 rather than the row dot's 1e-4: a tighter band would be measuring the
cache format, which is a decision, not an error.

The chain found one bug worth recording, because it is the kind that a
whole-layer relL2 reports as "everything is wrong": the norm pointers were
assigned to a local array instead of the handle, so every norm ran weightless
and the layer came out decorrelated at relL2 0.99. The stage probe located it
in one run, which is why the probe is part of the module and not a scratch
patch.

The timing is the honest part of this step. 0.57-0.64 ms for a sliding layer
and 0.68 ms for a full one project to 17.6-19.3 ms per token, 52-57 tok/s,
against the 10.97 ms the tools measured for the routed weight stream. The
projection is 25 sliding layers plus 5 full ones at two measured per-layer
costs, not a measured 30-layer step, and it says nothing about prefill. The
gap has a cause: a layer reads about 34 MB of weights here and runs in
0.57 ms, which is 59 GB/s, while the routed benchmark reads its 18 MB in one
launch shape at 128 GB/s. Each projection in the chain is its own small
launch, and the card is not saturated by a 2816-row matvec. Making the chain
faster is the next unit's work, and it is a launch-shape problem, not an
arithmetic one.

## Step 9c: the chain, priced per launch

Step 9b's per-layer number was a total with no breakdown, so the first thing
this step added was the breakdown: nine boundaries in the chain, recorded with
CUDA events on stream 0 (`gm4_gpu_layer_timing`, `gm4_gpu_layer_sections`).
An event record is a stream-ordered timestamp, not a wait, so the spans are the
chain's own timeline and no launch is serialised to measure it. The table
immediately named two costs nobody had guessed:

```
TIMING layer 0 Sliding 0.584 ms for one token (chain state 620 KiB)
  SECTION input norm + qkv           0.082 ms
  SECTION qkv norms + rope + cache   0.011 ms
  SECTION attention                  0.008 ms
  SECTION o_proj + residual          0.038 ms
  SECTION dense feed-forward         0.075 ms
  SECTION router norm + scale        0.005 ms
  SECTION router matvec              0.016 ms
  SECTION router top-k               0.126 ms
  SECTION routed experts             0.202 ms
  SECTION close                      0.011 ms
  SECTION sync + download            0.009 ms
```

The router's selection was 0.126 ms - 22% of a layer - for 128 experts and
k = 8, because `router_topk_kernel` did the selection on one thread: k rounds
of a serial scan over every expert with an inner scan over the already-picked
list. It is now k rounds of a 32-lane argmax, each lane scanning its own
strided slice, with the CPU's tie rule (`forward.rs:80-88`: highest first, an
exact tie to the lower index) written as the compare itself. 0.126 -> 0.009 ms,
and `ROUTER`'s picks and weights are unchanged.

The experts section was the second cost, and it was mostly op count: eight
`gelu_mul` launches, then per expert a clear, a down gather and an `axpy` -
38 operations for 9 MB of weights. Three shapes replace them:

- `gelu_mul_blocks_kernel`: one launch over all k blocks, indexed by
  `blockIdx.y`, the expert's 2*ff stride inside the kernel;
- one gather over the concatenation of the k down blocks (the row lists were
  already concatenated) and one `moe_reduce_kernel` that sums them with the
  router weights in the same k order the axpys used. This is exactly the
  reference engine's `v41_vq_reduce_kernel`
  (`/data/ds4-dfm-rs/cuda/ds41_vq_decode.cuh:179-185`), read first-hand;
- a per-row-block activation offset in the row kernel (`Layout.xrows`,
  `xcols`, applied by `row_x`), because a packed down gather gives each
  expert's rows a different activation. Without it the packed gather dotted
  every expert against expert 0's activation, which the layer gate caught at
  relL2 5.3e-1 before it was wired.

0.202 -> 0.125 ms. The last small win is that a tensor's first stage now
assigns its row instead of accumulating into it (`Layout.first`), which
deletes the eight output clears a layer used to need.

Attention is invisible at position 24 (0.009 ms: one key) and is not invisible
at a real depth. The step-9a gate measured 0.239 ms for a sliding layer's
1024-key window at position 1299. That kernel was one block per head - 16
blocks on 56 SMs - with the value pass as a 1024-iteration dependent chain in
one thread per dimension, 17 GB/s. It is now the flash-decoding shape:
`attn_split_kernel` runs one block per (head, run of the window), with the
number of runs chosen to reach 64 blocks (at least 64 positions per run), and
`attn_combine_kernel` rescales the runs' partials by `exp(m_s - M)` and divides
once. 0.239 -> 0.043 ms at 1300 positions, 0.097 -> 0.029 ms for the full
layer at 192, and against the f64 reference the answer is 2.187e-7 (it was
3.4e-7). The ring gate's `DENSE` check still reads exactly 0.000e0: a run is a
contiguous segment of the one ascending position walk, and the schedule
depends only on the head count and the window, so the dense walk and the ring
walk still choose the same runs and the same arithmetic.

```
LAYER 0 Sliding at 0:  relL2 1.510e-4     LAYER 0 Sliding at 24: relL2 2.409e-4
LAYER 5 Full at 0:     relL2 5.655e-5     LAYER 5 Full at 24:    relL2 9.057e-5
  TIMING layer 0 Sliding 0.380 ms | layer 5 Full 0.457 ms
  SECTION input norm + qkv 0.077 | qkv norms 0.010 | attention 0.009
  SECTION o_proj + residual 0.036 | dense feed-forward 0.067 | router 0.030
  SECTION routed experts 0.125 | close 0.011 | sync + download 0.013
LAYER PROJECTION 25 x 0.380 ms + 5 x 0.457 ms = 11.80 ms per token, 84.8 tok/s
```

Every band is the step-9b number to the digit, which is the point: these were
launch-shape and selection changes, not arithmetic changes. 17.56 -> 11.80 ms
per token, 57.0 -> 84.8 tok/s.

Two honest limits on that 11.80. It is a projection from two measured layers at
position 24, not a 30-layer step, and at position 24 attention is nearly free:
at a real depth a sliding layer's attention is 0.043 ms rather than 0.009, so
the projection becomes ~12.7 ms (79 tok/s) with 25 sliding layers at depth.
The head (262144 logits, 278 MB) is not in the projection at all.

One shape was tried and rejected, because the reference had already rejected
it. Every container here carries two VQ stages, so each matvec is two launches
plus a clear; fusing the stages into one kernel that reads both codebooks and
both index streams looked like free parallelism, and measured slower - layer 0
went 0.385 -> 0.439 ms. The reason is in the engine's own comment: one 64 KB
codebook fits a block's shared memory, two do not
(`/data/ds4-dfm-rs/cuda/ds41_vq_decode.cuh:217-219`). The per-stage launch is
the reference's shape for the same reason, so it stays.

## What the engine's MoE does, and what does not transfer

The ds4 engine's expert decode is worth recording here because it prices the
next shape. For a single token it runs one persistent kernel for the whole
expert stack, not one launch per expert
(`/data/ds4-dfm-rs/cuda/ds41_vq_persist.cuh:157-213`, chosen at
`ds41_vq_decode.cuh:331`): grid = the SM count, 1024 threads, work items are
(e, row) pairs cut into contiguous per-warp spans that never cross an expert,
the codebook and the activations are staged in shared once, and the kernel has
a single block-wide barrier for its whole life. The speed trick is the span
walk: consecutive rows of one matrix are contiguous in the bitstream, so a
warp reads its span as one continuous stream and never restarts at a row
boundary, which is what removes the per-row head stall.

That carries a precondition, stated in its own plan
(`docs/deepseek41-port-plan.md:708-711`): every row needs at least 8 rounds of
32 indices. Our gate/up matrix satisfies it (2816 cols, dim 8: 352 indices, 11
rounds) and already runs the block kernel at 128 GB/s. Our down matrix does
not: 704 cols gives 88 indices, 2.75 rounds, and `88 % 32 != 0`, so
`v3_blk_ok` refuses it (`gemma4_gpu.cu:1082-1084`, the tools' rule at
`/data/VQ_tools/c/gpu/decode-gpu.cu:66-68`) and it falls back to the generic
warp kernel, one warp per row with four byte loads per index.

The first thing this unit got wrong is worth keeping. Step 3's 73.3 GB/s for
that gather looked like the per-row head stall, so the next kernel was a span
walk - one warp over consecutive rows, the cross-row carry the engine's
version needs. Measured, the story is different:

- the 73.3 GB/s is the gathered 22528-row job through the ABI, a sync and a
  90 KB download wrapped around a 5.7 MiB read, not a kernel rate;
- the kernel's own rate on the whole 360448-row stack is 114.0 GB/s with the
  generic kernel's four-byte index read, and 132-133 GB/s once the read is
  three bytes (`gemv_rowspan_kernel`, variant 4: a min(nbit,12)-bit field at
  byte b needs at most 19 bits, so b[0..2] suffice);
- the span itself buys nothing on top: 1, 2, 4, 8 and 16 rows per warp measure
  130.2, 129.3, 132.5, 132.8 and 130.3 GB/s on that stack. The win was the
  read width, not the cross-row ILP, and 4 is kept only because it is not
  worse;
- in the token path this is invisible: the experts section is 0.125 ms before
  and after, because the routed down job is about 22 us of a 125 us section
  and 17% of 22 us is inside the section's own noise.

So the down matrix's short row is not what limits the token. The genuine
per-row cost is real but small next to the per-launch cost, and the honest
next lever is the launch count and the 30-layer loop, not this kernel.

## The finding: the CPU oracle halved every subnormal half

The first gate run failed at 4.5e-5 relL2, with the CPU the accurate side
(9.2e-7 from f64) and the device 4.5e-5. A one-hot probe isolated it: with one
activation column, a row's dot is a single stored value, and it still differed
by 2.6e-5.

Hand-decoding the payload settled it. Row 1429, column 0 of `q_proj`:

```
stage 0  index 383   codebook 5.155801773071289e-05   gain 1.0
stage 1  index 4077  codebook 0.0035457611083984375   gain 1.0
sum      0.0035973191261291504   <- the device's value
```

5.1558e-05 is a subnormal half. `crates/ds4-core/src/vq.rs`'s `f16_to_f32`
normalized subnormals starting from exponent field 112 instead of 113, which
halves every subnormal codeword. The reference is the producer's decoder,
`/data/VQ_tools/crates/vq-format/src/lib.rs:86-108`, which starts at 113; the
C function the comment cited (`ds41_vq_fmt.h:37-43`, `ds4vq_f16`) carries the
same off-by-one, and the Rust port inherited it.

Fixed in the family's decoder, with a regression test
(`tests/vq.rs::half_subnormals_are_exact`). After the fix the gates read as
above, every one-hot probe is exact, and the CPU forward still answers
"Stockholm".

The C `ds4vq_f16` in `ds41_vq_fmt.h` was not changed: it is the native
engine's decoder for the older VQ families, and correcting it would move their
recorded numbers. It is reported here so it can be its own unit, with its own
re-measurement, on the family it touches.

## Limits this unit leaves in place

- One host round trip per standalone call: the gated entry points still upload
  their inputs and sync, and the prefill takes transposed host activations and
  returns a host [ntok][rows] block, so a real prompt chunk copies twice. The
  layer chain is the exception and the shape the rest should follow; what is
  missing there is the 30-layer loop and the prompt's prefill path.
- No serving integration and no 30-layer step: one layer chains on the device
  now, but the loop over the 30 layers still lives on the host, and each layer
  costs a host activation copy in and out. The residency is all-or-nothing
  (9.0 GB), and the card has 1.5 GiB left at the measured moment, of which the
  session's KV costs 280 MiB at a 4096-position bound: workspace, prefill tiles
  and logits must fit in the rest.
- The kernels read the tools' DQV3 only. The engine's DQV3 (32-byte header,
  `cb_off`, fixed 12 bits) is refused by the payload check, as it is on the
  Rust side.
- The 11.80 ms projection is two layers at position 24. Attention is 0.009 ms
  there and 0.043 at 1030 keys, so a real depth is ~12.7 ms for the layers, and
  the 278 MB logits head is not in it at all.
- The down matrices (704 and 2112 columns, 88 and 264 indices) take the span
  kernel at 132-133 GB/s on the whole stack against the generic kernel's
  114.0; in the layer the difference is inside the section's noise, so the
  gathered path's 73.3 GB/s in the step-3 table is an ABI measurement, not a
  kernel one.
