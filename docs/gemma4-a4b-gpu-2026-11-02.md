# Gemma-4-26B-A4B device path, steps 1-3 (2026-11-02)

The CPU forward answers, at 1.26-1.33 s per token. This unit opens the device
path with the two things that must be true before a token can run there: the
whole artifact resident, and a row dot that agrees with the CPU oracle.

## What landed

- `native/gemma4/gemma4_gpu.h` and `native/gemma4/gemma4_gpu.cu`: map every
  RQVQ container the release names, check each header against the release's
  shape, upload every payload once with its own 256-byte-aligned slot and a
  zeroed 64-byte tail, and run one fused gather-and-dot per payload. The
  kernels are the VQ tools' own device code, ported for this payload:
  `gemv_v3blk` (block kernel, `/data/VQ_Tools/c/gpu/decode-gpu.cu:285-333`),
  `gemv_warp4` (dim-4 fast path, `:199-237`), `gemv_warp` (generic, `:619-656`),
  with `rd_idx_fmt` (`:110-133`) and the selection rule `v3_blk_ok` (`:66-68`).
- `crates/ds4-core/examples/gemma4_a4b_gpu_gate.rs`, behind the new
  `gemma4-gpu` feature: opens the release, lists every encoded container,
  prints the residency account, then gates two geometries against the CPU.
- `Makefile`: `tests/gemma4_gpu_gate`. The object is self-contained (no engine
  objects) and builds for this device (`-arch=native`) unless a `cuda-*`
  target has recorded an architecture.
- `gm4_gpu_rows` in the same header and module: the routed gather, one row
  list per call, every entry checked against the tensor's row count, gated
  against `Matrix::dot_rows` on both expert stacks.

`/data/vq-artifacts/gemma-4-26b-a4b-8x4096`.


The third column is the independent reference: the whole tensor decoded to f32
and dotted in f64. It is reported because agreement between two f32 paths is
not proof. The device is the more accurate side on both tensors, as a 32-lane
partial sum should be; the CPU's error is the sequential sum's.

The two geometries are picked by the tools' rule, not by hand: `q_proj` is
nc 4096, so the 12-bit stream and `nidx_row 352` satisfy `v3_blk_ok` and the
block kernel runs; the router is nc 256, whose 8-bit stream fails that
precondition and takes the dim-4 fast path.

Timing is per stack, host-to-host through the ABI (x upload, launch, sync, y
download), and is not a token time. For scale, the VQ tools' own `decode-gpu
--check` on the same q_proj container measured the block kernel at 0.0342 ms
(130.9 GB/s) launch-only, so the ABI's transfers and one sync cost about 6 us
of the 40. That is the next unit's business, not this one's.

## Step 3: the routed gather

A mixture layer routes each token to eight of 128 experts. Its two stacks are
`experts.gate_up_proj` at 180224 x 2816 (128 x 1408 rows) and
`experts.down_proj` at 360448 x 704 (128 x 2816 rows), both dim 8 / nc 4096, so
both run the block kernel. On the CPU the forward already gathers:
`Matrix::dot_rows` names the rows an expert needs (`weights.rs:107-127`).

`gm4_gpu_rows` is the same kernel with a row list. A warp's row is `rl[lo]`
instead of `row0 + lo` (`gemma4_gpu.cu`, `row_of`), so the launch costs one
extra load per row, not per index. Every entry is checked against the tensor's
row count on the host before the list is uploaded, because a row past the end
would read the next payload's stream.

```
GATHER ...experts.gate_up_proj 180224x2816 rows 11264 of 180224
       experts [0, 3, 17, 42, 64, 91, 120, 127]
       cpu 7.1 ms gpu 0.755 ms relL2 9.768e-7 maxabs 7.153e-6 scale 3.603e0
  F64 cpu 9.683e-7 gpu 1.087e-7 over 11264 gathered rows
  MIX interleaved 128 rows + repeat: relL2 9.284e-7 maxabs 3.338e-6
       repeat bit-identical true
  REFUSE row 180224: row 180224 at entry 0 is outside the tensor's 180224 rows
  TIMING best 0.093 ms of 3 launches, 11.4 MiB of the stack read at 128.0 GB/s
GATHER ...experts.down_proj 360448x704 rows 22528 of 360448
       cpu 4.4 ms gpu 0.241 ms relL2 4.877e-7 maxabs 5.245e-6 scale 6.248e0
  F64 cpu 4.788e-7 gpu 9.172e-8 over 22528 gathered rows
  MIX interleaved 128 rows + repeat: relL2 5.135e-7 maxabs 1.371e-6
       repeat bit-identical true
  REFUSE row 360448: row 360448 at entry 0 is outside the tensor's 360448 rows
  TIMING best 0.083 ms of 3 launches, 5.8 MiB of the stack read at 73.3 GB/s
```

The routed shape reads 11.4 MiB of the 182.3 MiB gate/up stack and 5.8 MiB of
the 92.2 MiB down stack: 1/16 of the bytes, which is why one layer's experts
cost 0.18 ms of device time as against 0.9-1.0 ms for the whole stack. The
down gather runs at 73.3 GB/s against gate/up's 128.0 GB/s because its rows
carry 88 indices instead of 352, so the fixed per-row cost (index read, gain,
warp reduction) is a larger share.

Three checks beyond the eight-expert comparison:

- the f64 reference over the gathered rows is built from `Matrix::row`, the
  per-row decode path, not from the batched path the CPU oracle used;
- `MIX` interleaves the first and last expert in opposite directions and
  repeats a row, so a gather that quietly read a contiguous range from row 0
  would pass the shape check and fail here; the repeat must be bit-identical
  and is;
- a row equal to the row count must be refused, and the printed message is the
  refusal.

## The finding: the CPU oracle halved every subnormal half

The first gate run failed at 4.5e-5 relL2, with the CPU the accurate side
(9.2e-7 from f64) and the device 4.5e-5. A one-hot probe isolated it: with one
activation column, a row's dot is a single stored value, and it still differed
by 2.6e-5.

Hand-decoding the payload settled it. Row 1429, column 0 of `q_proj`:

```
stage 0  index 383   codebook 5.155801773071289e-05   gain 1.0
stage 1  index 4077  codebook 0.0035457611083984375   gain 1.0
sum      0.0035973191261291504   <- the device's value
```

5.1558e-05 is a subnormal half. `crates/ds4-core/src/vq.rs`'s `f16_to_f32`
normalized subnormals starting from exponent field 112 instead of 113, which
halves every subnormal codeword. The reference is the producer's decoder,
`/data/VQ_Tools/crates/vq-format/src/lib.rs:86-108`, which starts at 113; the
C function the comment cited (`ds41_vq_fmt.h:37-43`, `ds4vq_f16`) carries the
same off-by-one, and the Rust port inherited it.

Fixed in the family's decoder, with a regression test
(`tests/vq.rs::half_subnormals_are_exact`). After the fix the gates read as
above, every one-hot probe is exact, and the CPU forward still answers
"Stockholm".

The C `ds4vq_f16` in `ds41_vq_fmt.h` was not changed: it is the native
engine's decoder for the older VQ families, and correcting it would move their
recorded numbers. It is reported here so it can be its own unit, with its own
re-measurement, on the family it touches.

## Limits this unit leaves in place

- One host round trip per call: no device-resident activation buffer, no
  chained launches, one sync and one row-list upload per gather. The model
  step will need the chain and a row list the router writes on the device.
- No prefill GEMM, no attention, no router top-k, no logits head, no serving
  integration. The residency is all-or-nothing (9.0 GB), and the card has
  1.5 GiB left at the measured moment: KV, workspace and logits must fit in
  that, which is why the workspace here is only two small buffers.
- The kernels read the tools' DQV3 only. The engine's DQV3 (32-byte header,
  `cb_off`, fixed 12 bits) is refused by the payload check, as it is on the
  Rust side.

## Reproduce

```
make tests/gemma4_gpu_gate
./tests/gemma4_gpu_gate --dir /data/vq-artifacts/gemma-4-26b-a4b-8x4096 \
    --timing 5 --onehot 0,33,351
```

nvcc is at `/usr/local/cuda/bin` and not on `PATH`; the Makefile uses
`$(CUDA_HOME)/bin/nvcc` directly. `/tmp` is a full 16 GB tmpfs on this host, so
builds need `TMPDIR` pointed at a real filesystem (`/data/tmp/build-tmp`).
