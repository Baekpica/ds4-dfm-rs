# GLM VQ direct BF16 KV handoff

Adopt direct BF16 KV projection/attention handoff on the selected KDA Q4_K
artifact. Four fresh processes in off/on/on/off order increase median decode
from **8.90 to 13.045 tok/s (+46.57%)**. Both optimized runs finish the
prefill-plus-decode workload faster than either control. No additional weight
quantization, cache allocation or arithmetic change is involved.

## Measured problem and change

The [Q4 baseline profile](glm53-vq-kda-q4-speed-2026-10-16.md) spends
1.145 of 3.557 decode seconds (32.19%) converting expanded KV from BF16 to
FP32 and immediately back. There are 352 calls in each direction across
11 DSA layers and 32 generated tokens. The latent cache also makes a smaller
BF16/FP32 round trip before projection.

The new [native DSA wrapper](../ds4_glmvq_gpu.cuh) projects the existing BF16
latent cache directly into BF16 expanded KV. The typed
[attention path](../cuda/glm_vq_attention.cuh) consumes it without conversion.
KV_B GEMM, QK GEMM, separate BF16 scaling, FP32 softmax, BF16 probabilities
and PV GEMM retain their original boundaries. Positions are still written
between projection and attention. Cache stores and ownership are unchanged.

Dispatch requires a BF16 weight record, matching head/dimension layout,
16-byte pointer alignment and leading dimensions divisible by eight.
Capacity checks precede enqueueing. Other supported formats/alignments and
`DS4_GLMVQ_KV_BF16=0` use the previous unpack/project/attend sequence.
The default is enabled. Temporary allocations retain their previous sizes;
this change neither adds an expanded-KV cache nor qualifies CUDA capture.

At the first decode position, the removed conversions account for
`12 * 1985 * (32768 + 512) * 11 = 8,720,025,600` logical bytes/token.
The factor 12 counts reads and writes of both conversion directions.
This is traffic implied by tensor operations, not a measured DRAM counter.
The existing isolated conversion profile measured 3.167 ms per expanded-KV
pair at one layer, 246.42 GB/s of logical traffic. Its NCU record is reused:
16 registers, about 79–84% occupancy, no available DRAM-byte counter.
No further NCU run is needed for work that has been removed.

## Matched whole-workload results

Artifact: `GLM-5.3-Flash-VQ-Q4K-KDA-GGUF`, manifest
`6ea4054b04cfb1bd2e26db318e022a5918b49c8002d7d5e1cf17e502a074a044`.
Only the previously selected 136 nonexpert KDA Q/K/V/O matrices use Q4_K;
all routed/shared experts, codebooks and KV_B matrices are unchanged.

Every run uses the same executable and actual CUDA/cuBLAS mappings, 1,984
raw-code input tokens, 32 forced non-EOS greedy tokens, context 2,048,
chunk 1,024, MTP/capture off and one in-process VMM owner. Processes are
fresh; OS file-cache state is inherited. Busy GPU clocks are 2,184–2,190 MHz
under the preserved 300–2,200 MHz policy.

| Handoff | Order | Prefill tok/s | Decode tok/s | Phase sum, s |
|---|---:|---:|---:|---:|
| Off | 1 | 420.75 | 8.89 | 8.315 |
| On | 2 | 421.89 | 12.84 | 7.195 |
| On | 3 | 427.93 | 13.25 | 7.051 |
| Off | 4 | 320.18 | 8.91 | 9.788 |

Median phase sum falls from 9.051 to 7.123 s (-21.30%). This includes
variation in prefill: the final control is much slower there. An intrinsic
14.70% prefill gain is **not established** by the median throughput change.
Both optimized phase sums beat the fastest control by 13.47–15.20%, and
neither optimized run shows a prefill regression. Decode improves repeatedly.
Do not attribute the unprofiled control's prefill slowdown to a specific cause.

Phase sums are inferred from rounded rates, excluding loading/proof-file
output. Process wall times are 199.27, 204.85, 192.16 and 250.94 s in order;
these do not establish a startup improvement. `first_token_sec` measures
the first decode call, not HTTP TTFT. The workload preserves all 33,356
MMA work items and records 374 direct KV calls per optimized run.

## Numerical and state scope

The [native fixture](../tests/test_glm_vq_kv.c) uses the actual layer-3 KV_B
payload, SHA256
`f0540a2685b23735442058523c7fca84e6e58096b06db07fa7d2725616d8c7de`,
with distinct synthetic BF16 query/latent inputs. It compares the new
wrapper's off/on paths against the old explicit production sequence at
widths 1/7/64/960/1,024 and key counts 1–2,016. All 33,832,960 output values
per arm agree, all cache bytes and causal positions are preserved, and
unaligned fallback and invalid geometry/capacity checks pass. Seven direct
calls confirm the candidate actually executed.

All four full runs have finite, identical 154,880-entry frontier logits
and identical 32 generated IDs. Exactness is inexpensive here because the
changed operations only copied BF16 values through FP32. It is not a new
bit-identity requirement for approximate inference. Existing packing,
Q4/MMA/KDA and arithmetic proofs were reused. The user's accepted
[Q4 quality tradeoff](glm53-vq-kda-q4-2026-10-16.md) remains recorded;
its earlier quality screen was not repeated.

## Retained profile and provenance

The retained Nsight Systems run reports 424.69 prefill / 13.16 decode tok/s.
Its prefill/decode NVTX spans are 4.672 / 2.432 s. The expanded-KV conversion
class falls from 44 to zero prefill calls and from 704 to zero decode calls.
Including latent input conversions removes 1,408 decode launches. This
comparison reuses the earlier Q4 trace to identify removed work; the four
same-final-binary plain runs establish the speed gain.

GPU idle is 0.075 s (3.09%); it is an upper bound on host gaps, not an
isolated dispatch measurement. Category attribution follows graph launch
order; synchronous API time overlaps GPU work.

Remaining dense costs include cooperative Q4 projection 0.389 s, full-prefix
BF16 KV_B expansion 0.378 s (15.56% of decode), and direct FP8 projection
0.358 s. The full-prefix reconstruction is the next decode investigation;
removing it requires assessing reuse or a changed attention factorization,
not another format-copy kernel. Prefill still spends 1.512 s in routed VQ
and 1.100 s (23.55%) in the KDA recurrence. These are measured remaining
costs, not claims of additional optimization.

Peak DEVICE allocation remains exactly 76.508 GiB, with a closed allocation
ledger. Minimum system available memory is 39.075 GiB. These describe
unified memory and must not be added as separate CPU RAM and VRAM.
The same 71 initial `cudaMalloc` calls take 0.054 s in this trace, versus
1.740 s in the earlier Q4 trace; allocation capacities/counts did not change.
That variability must not be credited to the KV handoff as a prefill gain.
Profile frontier logits and generated IDs also match the plain candidate.
