## Protocol

- One fresh process per (side, context) cell.  A calibration probe of 8,192
  bytes (one output token) runs in a sweep's first boot only, to measure the
  corpus's bytes-per-token ratio rather than assume it; every later cell
  reuses it.  Two sweep invocations ran, so two calibrations exist -- the
  cell quoted below is the port sweep's (the curve sweep's: 2512 tokens,
  3.8 s, 665.9 t/s).
- Per cell: turn 1, then turn 2, which repeats turn 1's messages and
  appends the assistant's answer plus a short new user turn.  The prefix is
  message-identical; a byte-identical tokenized prefix is not asserted (the
  answer is reloaded with `jq -r`, which appends a newline).  On this route
  `prefill_cached_tokens` reads 0 regardless, so the leg's purpose is the
  full-re-prefill measurement itself.
- Up to 128 greedy tokens per request (`max_tokens` 128; the harness does
  not assert the generated count, so the decode rates are conditional on
  the generated length), temperature 0, `reasoning_effort: none`.
- The graphics clock is sampled per request; only turn 1's median enters
  the structured record in this pass (turn 2's clock medians were not
  captured), so the clock note below is turn 1's.  One run per cell: single
  samples, not interleaved repeats.
- Two rates are reported and they are not the same measurement.  The
  response's `prefill_tok_s` divides by `prefill_ms`
  (`crates/ds4-server/src/stream.rs:366-369`), the first token minus `t0`,
  while `ttft_ms` is the first token minus arrival
  (`crates/ds4-server/src/generate.rs:3194-3195`); the server's own
  `[v41] prefill` line times the prefill phase alone.  The line rate is
  quoted first below and both are given.

## What the profile said (CORRECTED 2026-10-11)

The first version of this section subtracted the final block's `[v41-prof]`
total from the whole-request prefill and read the remainder as "outside the
layers".  That subtraction is invalid: a non-final chunk sets `ced_skip` and
returns at the CED edge (`ds4_ds41_forward.inc:979-987` -- hc_half plus
`v41_attention_kv_only` plus flush, then return) BEFORE the `[v41-prof]`
emitter (`:1031-1037`), so only the last block ever prints a total and every
earlier block's executed layers (L0..19 plus the KV-only edge) sat inside
the "outside" remainder.  An independent check (gpt-6.1-sol subagent,
2026-10-11, VERDICT: FAIL) and the raw logs agree; the claim is retracted.

The per-block progress lines close the wall instead.  Elapsed at each
block's last printed layer (`L19` = the CED block's layer before its
KV-only edge; `L39` = the full block's last layer), against the native
prefill line:

| cell | blocks (pos0+n) | last printed layer, elapsed | prefill line |
|---|---|---|---|
| 354 t1 | 0+392 | L39 0.8 s | 0.8 s |
| 354 t2 | 0+537 | L39 1.0 s | 1.0 s |
| 839 t1 | 0+925 | L39 2.2 s | 2.2 s |
| 839 t2 | 0+1070 | L39 1.9 s | 1.9 s |
| 2048 cal | 0+2048, 2048+464 | L19 2.8 s; L39 1.1 s | 3.8 s |
| 2048 t1 | 0+2021, 2021+128 | L19 1.8 s; L39 0.4 s | 2.2 s |
| 2048 t2 | 0+2048, 2048+246 | L19 1.8 s; L39 0.6 s | 2.4 s |
| 8192 t1 | 4x2048, 8192+257 | L19 2.8/1.8/1.9/1.9 s; L39 0.8 s | 9.2 s |
| 8192 t2 | 4x2048, 8192+402 | L19 1.8/1.8/1.9/1.9 s; L39 1.0 s | 8.4 s |

Sums match the prefill line in every cell (0.1 s rounding; the CED edge
layer and per-block setup are the only terms not individually printed).  The
prefill IS executed layer work; there is no large outside-layer term.  It is
also not residency: the boot line reports `materialize base: funded 87/87
promote units (0 unfunded), populated 87 (105.75 GiB)`.  The VQ prefill runs
on the tensor-core path and the engram rows go through `io_uring` (one
submit per round, depth 512; two engram layers, 384,006,168 and 384,016,682
rows on disk) -- and those reads execute INSIDE the layer times, not outside
them.

Corrected cost shapes:

- A full 40-layer pass costs 1.8-3.4 ms/token over 128-1070-token blocks
  (`[v41-prof]` totals: 392 tok 782.3 ms; 464 tok 1082.9 ms; 925 tok
  2237.3 ms; 128 tok 434.2 ms; 257 tok 797.4 ms; the 537/1070/402-token
  cells are bounded by their L39 lines).  The earlier "small blocks pay
  several times the per-token cost" compared layer-only milliseconds
  against whole-request wall seconds per token and is withdrawn.
- A warm CED block (L0..19 plus the KV-only edge, 21 of 40 layers) costs
  0.88-0.93 ms/token at ~2048 tokens (1.8-1.9 s), so requests past the
  chunk cap are CED-dominated; that, not a small-block penalty, is why
  2048-plus requests look cheaper per token than single-block ones.
- The first prefill block of a process is cold: 2.8 s against 1.8 s for the
  same 2048 shape, 2.2 s against 1.9 s at ~1k.  One warm-up prefill per
  process would move that cost off the measured turn.

The block-reread inference (384 experts x 3 x 2304 x 5120 = 13.6B
parameters per layer, ~2.55 GB at 1.5 bits, ~102 GB per full 40-layer
pass) remains an untested hypothesis: CED blocks execute only 21 of 40
layers, so per-pass traffic must be counted per executed block, and the
traffic itself was never measured.

Decode rounds print 44-97 ms per `[v41-prof]` round at widths 1-6 with pos
deltas 1-3 (e.g. 2149+6, 2150+2, 2152+3).  Multi-token decode forwards
therefore exist, while `tok_per_step` reads 1.000 and the host-gaps line
reads `samples 0/0 rounds` / `0 graph rounds`.  What these widths are and
why the probe reads 0 is the first question of the speculation unit; the
"no speculation ran" statement below is withdrawn pending that
reconciliation.

## Body-end marker probe (2026-10-11, same day)

The corrected accounting left only the CED edge and per-block setup open
(0.1 s rounding).  A prof-only marker was added to the engine (commit
`40dc337`: the CED return prints its own total; the full arm tags its line
`full`), and the 2048 cell was re-run unchanged (`/tmp/ds41_perf_marker`,
same invocation; probe binary sha256
`39d3dd4480ef0bf3bc884beab85dc20802ebd176af6e1575d6f5abbe3c131227`, the
pinned `4009bd78` binary kept at `/tmp/ds4-server.pinned-4009bd78`).
Per-request closure, milliseconds:

| request | CED block (edge included) | full block | sum | prefill line |
|---|---:|---:|---:|---:|
| cal 2512 | 2763.4 | 1092.9 | 3856 | 3.9 s |
| t1 2149 | 1794.0 | 433.7 | 2228 | 2.2 s |
| t2 2294 | 1788.7 | 650.1 | 2439 | 2.4 s |

The accounting closes to <= 0.05 s on every request; the residual is
token/position upload, pre_mix, feed prepare and drain.  The CED edge and
its flush cost <= ~50 ms (inside the CED totals; the cal CED total 2763.4 ms
is within the 0.1 s rounding of its L19 progress line).

Cold decomposition (first request of the process): the first CED block
costs 2763.4 ms against 1788.7 warm (+975 ms), and the first full block's
layer 0 spikes to 219.3 ms (warm: 21-25 ms).  A warm-up prefill at boot
would move both off the first measured request; diagnosing them is open.

The probe reproduces the original pass within noise (line rates 651.2 /
964.6 / 940.6 t/s, decode 39.9 t/s, `tok_per_step` 1.000), and it leaves
per-layer tables for every full block in the logs (the `[v41]` progress
lines carry cumulative per-layer elapsed for CED blocks).

## Engine-side cell and port-engine parity (2026-10-11, same day)

The engine side was swept for the first time through the same harness
(`/tmp/ds41_perf_engine`, same corpus, 2048 cell; engine binary sha256
`53156c14570be6512cfbe6a483e1a7736a47c277971f3325f0161df309ef2bce`, the
source-built oracle).  The engine boot carries no `--v41-prof`; its
per-layer progress lines are unconditional and carry the deltas below.

| side | cal 2512 | t1 2149 | t2 2294 | decode | clock |
|---|---|---|---|---|---|
| engine | 3.4 s / 732.8 t/s | 2.2 s / 959.4 t/s | 2.5 s / 930.8 t/s | 43.9 t/s | 2440.5 MHz |
| port | 3.9 s / 651.2 t/s | 2.2 s / 964.6 t/s | 2.4 s / 940.6 t/s | 39.9 t/s | 2450.5 MHz |

Warm turns are at parity (the port marginally ahead); the cold first
prefill costs the port ~0.4 s more than the engine; decode is ~9% behind
and is an open item.

Per-layer, the engine's CED block at 2048 shows the SAME signature as the
port's: `L01 +0.4 s` while every other layer is 0.0-0.1 s, and the same
1.8 s L19 end.  The L1 stall is therefore inherent to the engram design at
this block width, not a port deficiency: the first engram layer waits for
its round (~98304 aligned reads) with only L0's compute to hide it.  The
engine records a 60-70 ms residual idle for the same shape
(`core_v41_engram.c:118-119`, 2026-09-29) that does not reproduce today;
its own comment names the never-implemented fix: prefetch the next block's
rounds one block ahead (`v41_engram_prefetch_next`, referenced at
`core_v41_engram.c:230`, absent from the tree).  That is the measured
prefill lever: ~0.3 s of a 1.79 s CED block at 2048 (~17%), repeated per
block at longer contexts.

## Limits and open boundaries

- No prefix reuse on this route.  Every turn 2 reported
  `prefill_cached_tokens 0` and re-prefilled the whole conversation: at 2048
  that is 2294 tokens and 2.4 s to add a ~145-token suffix.  This is the
  cost an agent session pays per turn, and it grows with context.
- Speculation status unresolved.  `tok_per_step 1.000` and `0 graph
  rounds` in every cell, but decode forwards run at width 1-6 (above), so
  "the draft never fired" is withdrawn; the decode numbers here must not be
  described as either drafted or undrafted until that probe is reconciled.
- Clock medians were 2437-2447 MHz, above the 300-2200 MHz user-managed
  range this host documents; the card's maximum is 3003 MHz.  The range
  should be reconciled before these numbers are compared with the qwen38
  records.
- The environment differs from the qwen38 records on this host, which
  quote driver 610.43.02 and CUDA 13.3; this pass ran on 580.142 and 13.0.
  Cross-family comparisons need that reconciled.
- One run per cell, single samples, no interleaved medians.  The engine side
  now has its 2048 cell (the parity section above); 32K and 64K have not
  been reached.  (The artifact sha256 was computed after the pass; the
  header carries it.)
- The block accounting is closed exactly (see the marker-probe section).
  What remains open: the ~40-50 ms per-request setup residual, the cold
  first-block terms, and the per-phase host counters (uploads, pre_mix,
  feed prepare, drain, io_uring depth).  Engram stays enabled in every run;
  no bisect.
