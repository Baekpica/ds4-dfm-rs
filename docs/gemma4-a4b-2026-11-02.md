# Gemma-4-26B-A4B: the family folder and the artifact contract (2026-11-02)

A new family folder, `crates/ds4-core/src/gemma4_a4b/`, reads the dense-VQ
artifact published by the VQ tools repository. This record covers the folder
and its contract validation. It does not claim a forward pass, logits,
tokenizer, chat protocol, vision sidecar or serving surface; those are later
units and the family is not serviceable yet.

## Why a new folder, not the H3 tower

`crates/ds4-core/src/minimax_h3/gemma.rs` is the MiniMax-H3 video pipeline's
fixed 48-layer INT8 text tower (its own constants at `gemma.rs:36-72`), built
for that pipeline's hidden-state capture. It is not a ds4 model family and was
not made to load this artifact. The family convention is the `*_vq` module
root plus folder: `ling31_vq.rs` with `ling31_vq/{config,layout,model,release}`,
registered through `identify_gguf` (`identify.rs:207-219`).

## What the artifact states

Read from `vq-release.json` (`schema vq-release/1`, written by
`vq-family release`, VQ tools commit 695069c):

- 657 text entries: 296 encoded containers (RQ VQ, f16 codebook, dim 8 /
  nc 4096 / 2 stages; the router at dim 4 / nc 256) and 361 copied RQVF f32
  sidecars; 9,569,465,828 bytes; fingerprint
  `3ea19748bdd122a0585f5e120c05b260869fb752ca5fedeee482bb03db6d0a5c`.
- 30 layers: 25 sliding and 5 full (`config.json.text_config.layer_types`),
  22 bound roles on a sliding layer (21 plus `v_proj`) and 21 on a full layer
  because `attention_k_eq_v` derives the value from the key.
- Query width 4096 sliding / 8192 full; key width 2048 / 1024;
  `experts.gate_up_proj` 180224 x 2816 (128 experts of gate and up at 704
  rows); `experts.down_proj` 360448 x 704; dense MLP 2112.
- Every release entry is `part: "text"`. The vision tower is absent by the
  family contract (`families/gemma-4-26b-a4b.json`, sidecar vision), so a
  non-text part is named and not bound.

## What landed

- `config.json`: the reference checkpoint's configuration copied verbatim
  (sha256 `ed0c1eb3633de771906e9ba004a44cc5635bcc06ee2062077c3d2e88a50707d3`).
  `config.rs` parses the fields the layout needs and derives the per-layer
  geometry: head width, KV heads, rotary width (full layers rotate 128 of
  512), theta, `k_eq_v`.
- `release.rs`: reads the release, checks the schema, the fingerprint and
  manifest digest shape, every entry's kind and geometry, the totals against
  the entries, each file's exact size, each RQVQ header (dim, nc, stages,
  groups, codebook, payload accounting) and each RQVF sidecar's shape. The
  payload byte arithmetic is the writer's own
  (`/data/VQ_tools/crates/vq-format/src/lib.rs:520-560`). `verify()` re-reads
  every sha256; `open()` does not, so opening a 9.5 GB artifact stays cheap.
- `layout.rs`: name -> role for the text set, one role table per layer, each
  shape checked against the configuration, `v_proj` required exactly where
  `k_eq_v` does not derive it, unknown names refused, non-text parts named.
- `model.rs`: `Family::open` (release -> configuration -> layout) and
  `is_release` for the identification chain.
- `examples/gemma4_a4b_open.rs`: opens the reference artifact and, with
  `--verify`, re-reads every digest.

## Gates run

- `cargo test -p ds4-core --lib gemma4_a4b`: 15 passed.
- `cargo check -p ds4-core`: clean.
- The example on `/data/vq-artifacts/gemma-4-26b-a4b-8x4096`: opens 657
  entries, reports 25 sliding / 5 full layers, full layer 5 with q 8192 x 2816,
  k 1024 x 2816 and no `v_proj`; `--verify` reports every sha256 matches
  (132 s, debug build).

The negative tests name the field: a wrong full-attention query width, a
missing `v_proj` on a sliding layer, a `v_proj` on a full layer, an unknown
text tensor, a container/release shape disagreement, a wrong totals sum, a
truncated sidecar and a wrong digest each fail with the tensor or field named.

## What this does not do

No forward pass, no attention kernels, no MoE routing, no logits, no
tokenizer ids, no chat protocol, no OpenAI route, no vision sidecar. The
module is not yet in `ModelFamily`/`identify.rs`, so `ds4` cannot select it;
that registration is the next unit, followed by a CPU reference forward and
its logits gate. The serialized attention geometry (two head widths in one
`Shape`) is the first thing that registration must solve: `Shape` carries one
`n_head_dim`, while this family needs one per layer type.
