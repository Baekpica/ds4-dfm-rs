# GLM VQ fused FP8 decode projections

The retained original-artifact path spends 69.16% of decode time in
projections. FP8 restoration alone takes 1.1994 s of 5.7343 s (20.92%)
in the saved 1,984+32-token trace. These FP8 weights belong to shared
experts, the first three dense FFNs and DSA projections. KDA Q/K/V/O
weights are BF16. This change preserves every artifact byte and precision.

## Implementation

YoungAi `7fb26cc332d740416792204a29c7d13d2986caf5`,
`src/cuda/cuda_v41_q4k.inc.cu:12-15`, motivates complete coalesced cache
lines. Here each lane loads eight adjacent FP8 bytes; a warp covers
256 contiguous bytes. Hardware E4M3 conversion, F32 block-scale
multiplication and BF16 rounding feed FP32 dots in registers. No expanded
BF16 weight matrix is written and reread. Input and output retain BF16
rounding; FP32 accumulation order changes. This is not FP8 matrix arithmetic.

The specialization handles single-token BF16 math on eight measured
original-artifact shapes with aligned pointers. It uses eight warps per
output row except the rank-1536 Q projection, which uses two. Other shapes,
formats, alignments and token widths retain restore+cuBLAS. Session scratch
and admission remain unchanged; the kernel adds no allocation. The diagnostic
fallback switch is `DS4_GLMVQ_FP8_DIRECT=0`; eligible N1 calls default on.

Shared-input staging was slower in both initial target shapes and is kept
only in the isolated diagnostic harness. Earlier VQ prefill uses measured
asynchronous double buffering; the FP8 decode path does not copy that
strategy without a benefit.

The 179 eligible matrices per decoded token contain 2,617,245,696 FP8
weight bytes. The previous implementation additionally wrote and reread
5,234,491,392 BF16 bytes each. These are logical execution traffic counts,
not measured DRAM traffic; scale, input, output and cache effects differ.

## Current trace and decision

A final Nsight Systems trace records 7.34 decode tok/s and 288.33 prefill
tok/s. The slow prefill is localized: GPU work is 4.775 s versus 4.702 s
in the saved combined baseline, while GPU idle increases 0.243→2.106 s.
The first prefill kernel starts after 1.796 s, versus 0.044 s previously.
One `cudaMalloc` alone takes 1.150 s. Both traces allocate the same 71 device
buffers, in the same size order, totaling 1,654,364,864 bytes during prefill.
The underlying reason for allocator-latency variation is unproven; host
memory-pressure spikes coincide with the slower fresh runs.

FP8 direct calls are zero in prefill. Its 716 FP8 restores and all prefill
kernel-group launch counts match the retained baseline. Decode instead uses
5,728 fused calls and no FP8 restore, removing 17,184 launches. Projection
GPU time falls 3.966→2.614 s; other decode stages are similar. This is
attribution across two builds with the same instrumentation, not an extra
matched speed pair. The six same-binary runs above establish the speed gain.

Current decode time is 4.362 s: projections 59.94%, attention/KDA core 19.59%,
VQ 7.38%, output head 5.27%, mHC/norm 4.07% and routing 1.73%. GPU idle is
0.075 s. Peak traced DEVICE allocations remain 81.72 GiB; system available
memory bottoms at 34.35 GiB. Those allocation events exclude driver, static
module and OS storage, and are not CPU RAM plus VRAM. Busy clocks remain
2,184–2,190 MHz.

Enable the guarded N1 FP8 path: its repeated decode and total-inference
benefit adds no workspace or weight-precision loss. The explicit-on checks
also cover the default-selection edit; no model checks are repeated for
that edit. The measured cold-prefill timing variance remains visible, and
strict code-only formatting remains a known limitation. Neither is reported
as a passed broad release gate. The current trace separates initial allocator
wait from unchanged prefill GPU work; it does not prove that all future
cold requests avoid the wait.

The next optimization round must address the retained path's current costs.
BF16 KDA Q/K/V/O alone contain 9,126,805,504 logical weight bytes per decoded
token, so expert-only VQ speed is not a model-wide bandwidth bound. Dense
projection traffic, repeated latent-KV expansion and initial allocation
latency need separate attribution before choosing another change. DeepSeek
parameter count or throughput is not a GLM performance guarantee.
