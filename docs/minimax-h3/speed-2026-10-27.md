# MiniMax-H3 speed baseline — the port against h3.c, 2026-10-27

The control table for the H3 speed campaign: the same checkpoint, the same
host and the same job on both engines, with each row labelled by the quantity
it actually is. The two engines do not count the same things, and the earlier
comparison that read 0.573 s next to 37.7 s was comparing a device counter
with a wall clock (see [The text phase](#the-text-phase-is-the-drive-closed),
which closes that gap).

Functional qualification of the port is
[validation-2026-10-26.md](validation-2026-10-26.md); this file records speed
and nothing else.

## Identities

- Port: this repository, commit `30262485`, binary `h3-rs` built on the Spark
  with `make h3-rs` after `rm -f native/h3/*.o`, so all four CUDA objects carry
  `-gencode arch=compute_121a,code=sm_121a`
  (`native/h3/*.o` timestamps 16:42, tree `.ds4-cuda-config.mk` `CUDA_ARCH := sm_121`).
  Binary SHA256 `52d2bbb8e7fc64e81bb23b58a856a16b66578ba25e7adc5109a5b8ad2ad7c6ab`.
- Reference: [h3.c at
  eae5d54](https://github.com/matrixfede/h3.c/tree/eae5d54e3a0419064b64171dcaebcfd92e9f3f63),
  copied to the Spark unmodified, `make -j$(nproc)`, no cuDNN in either engine:
  the reference's `Makefile:29-31` leaves `CUDNN_ROOT` and `CUDNN_FRONTEND_ROOT`
  empty, so `H3_USE_CUDNN` is never defined, and this port has no cuDNN wiring
  at all. Both engines therefore run the shared scalar attention. Nothing about
  the install was refused; see the handoff's Phase 5, which has the reference's
  own `H3_USE_CUDNN` recipe.
  Binary SHA256 `e382787c248741001c0de8b3d309eae4b8789ff2ee6cd4d35e2777a9a366bdaa`.
- Host: NVIDIA GB10 (Spark, `gx10-e1d2`), driver 580.178.04, CUDA 13.0, 48 SMs.
  Clocks observed during the paired run: SM 2,398 MHz on the port arm and
  2,405 MHz on the reference arm, 96% utilization on both, no throttle reasons
  active (`nvidia-smi`; the hardware maximum it reports is 3,003 MHz). That is
  above the 300–2,200 MHz range AGENTS.md records for this host, and the applied
  policy could not be read (`sudo -n nvidia-smi -q -d CLOCK` returned nothing),
  so the two arms are comparable to each other while the absolute range is
  unverified.
- Checkpoint: `/mnt/h3-artifacts/MiniMax-H3`, ext4 on `/dev/sda`, a USB SSD.
  That device is a phase in its own right: the prompt encoder reads 50.316 GB

- Measured ceilings for the same host (`tools/gb10_peaks`, `~/h3-peaks.txt`):
  BF16 `mma` 122.9 TFLOPS, L2 read 2,101.9 GB/s, DRAM streaming 236.8 GB/s.

Every stderr line is stamped with wall seconds, because the reference's own
phase lines are counters, not clocks:

```sh
stamp() { while IFS= read -r l; do printf '%s|%s\n' "$(date +%s.%N)" "$l"; done; }
{ "$REF" ... 2>&1; } | stamp >> run.log
```

The port prints its phases itself (`TEXT`, `LOAD`, `DENOISE`, `AUDIO`, `FRAMES`,
`VIDEO`, each with `seconds=`), so a port row needs no stamping; a reference
row needs the stamp for the phase and its own line for the counter.

## The text phase is the drive (closed)

The earlier row read "port 37.774 s against the reference 0.573 s, +37 s
un-attributed". That pair is not a comparison:

- The reference's teardown line (`h3_gpu_cuda.cu:308-318`) prints
  `gpu_seconds`, `command_encode_seconds` and `command_wait_seconds`, and those
  accumulate only inside an `h3_gpu_begin` / `h3_gpu_submit` pair
  (`h3_gpu_cuda.cu:611-641`). The encoder's weight reads happen on the host,
  outside those pairs, so the line reports device work only. Measured on job B
  (256×256, 22 frames, 2 steps, both engines on one timestamped stream): the
  reference's phase line arrived at wall 77.664 s, its encoder phase having
  started at 48.756 s — a **28.889 s phase** whose own counter reads
  `0.550202s GPU, 0.327984s encode, 0.222455s wait`.
- The port's `TEXT ... seconds=` is a wall clock around the whole
  conditioning step (`crates/ds4-core/src/minimax_h3/engine.rs:204-246`),
  including the 50.316 GB read.

The phase is the read. The prompt encoder executes layers 0..49 plus
`embed_tokens`: 50.316 GB of the shard set's 66.716 GB. Measured today on the
Spark, the same 14 shards read plainly with eight lanes (`dd bs=8M`,
`xargs -P8`):

```text
66,714,912,872 bytes in 29.173 s = 2.29 GB/s   (page cache holding 114 GB)
```

The port's own walls for that phase track the drive, not the code: 10.938 s
when the encoder set is resident (job B today, after the plain read above),
27.127 s (256×256), 28.276 s (512×512) and 28.479 s (job A today) when it is
not. Per the earlier session's record, the cold eight-lane rate for the same
set is 1.81–1.83 GB/s, and the port's 28.9–30.1 s cells equal 92–96% of it.

Conclusion: the port's text phase is at the USB SSD's transport limit, the
reference does the same read at the same limit (its own cold run in
`/tmp/gate-head.txt` reports the encoder at 24.694 s wall and a later one at
50.335610 s), and the earlier "+37 s" row is retracted. Actions available on
this phase are worth ~2 s of a 400 s job.

## What the phase boundaries mean

The two engines do not cut their phases at the same lines, which is why a
per-phase table must be read with care:

- The reference's `H3 DiT: load 20.019818s` covers `refine text`,
  `precompute AdaLN` and `load transformer core` together (job B: 0.52 + 8.06
  + 11.43 s). The port's `LOAD` covers the layout, the text refiner
  (`crates/ds4-core/src/minimax_h3/dit.rs:1555`, `h3_dit.c:1655-1665`), the
  AdaLN tree, the rope tables and the resident graph, and prints one number for
  all of it.
- The reference's `video VAE decoder` and the port's `FRAMES` are the same
  decode; the reference's `FFmpeg` and the port's `VIDEO` are the same mux.

## The page cache decides every read-bound row

Both engines read the checkpoint from the same USB SSD, and their working sets
do not fit together: the DiT is 61.7 GiB and the encoder set is 66.7 GB against
128 GB of RAM. Each engine's own load evicts the other's pages, so a row
measured right after the other engine is warm and the same row measured cold is
several times slower. Measured today with one binary, the same 61.7 GiB DiT
read cost 40.454 s on job B (cold, right after an unrelated read filled the
cache) and 7.234 s on job A (warm, the reference having just left the DiT
resident); the shape does not change that read, and job A's larger activation
set only makes the warm figure the smaller of the two comparisons.

Method for every later row: record `free -g` at each boundary, state the run
order, and compare read-bound rows only between runs of the same cache state.

The denoise row needs that treatment too, contrary to what this file first
claimed. Neither engine holds the whole 61.7 GiB DiT in device memory: measured
mid-denoise, the port's `h3-rs` held 9.9 GiB and the reference's `h3` held
39.7 GiB (`nvidia-smi --query-compute-apps=used_memory`). The port's BF16 block
weights are streamed by design (`dit.rs:60`, `LoadMode::Stream` at
`dit.rs:1576`), so every step re-reads them out of the page cache over the
coherent link: roughly 0.26 s of a 418 s step at the measured 236.8 GB/s DRAM
rate, but up to ~27 s per step if those pages are evicted and the read falls
through to the USB SSD. The reference reads the same file inside its own load
instead (20.09–23.70 s against the port's 7.23 s warm), and its counter splits
the 903.787 s denoise into 452.179 s of host command encoding against 451.648 s
of GPU wait. The two engines do not move the same bytes at the same time, so
the per-phase walls are the only directly comparable figures.

## Denoise — the row the campaign is about

Per-step cost of the port by token count, one row per shape:

| Tokens | Shape, frames | s/step | Where the number comes from |
|---:|---|---:|---|
| 448 | 256×256, 22 | 0.67 | `~/h3-run-256.log` (1.346 s / 2) |
| 4,352 | 512×512, 56 | 26.10 | `~/h3-run-512.log` (52.201 s / 2) |
| 18,432 | 768×768, 107 | 418.44 | today's paired run (836.886 s / 2) |
| 2,048 | 256×256, 107 | 9.08 | earlier session; no log retained on the host |
| 8,192 | 512×512, 107 | 92.6 | earlier session; no log retained on the host |
| 32,256 | 1344×768, 107 | 1,406.6 | earlier session; no log retained on the host |

The three unsourced cells are an earlier session's sweep at 107 frames, and no
log for them survives on the Spark; they are quoted as that session's record
and must be re-measured before any projection leans on them. Through the three
cells that are sourced, per step ≈ 1.38e-6 × tokens² inside ~11% (418.44
measured against 468.8 fitted at 18,432), and the quadratic term is the
attention.

The quadratic term is the attention, and it is nearly the whole step. nsys on
the port (512×512, 2 steps, `~/h3-nsys-stats.txt`) attributes 48.6% of GPU time
to `h3d_attention_tiled_kernel` (47.19 s over 102 calls, 463 ms each), 24.4% to
the video VAE's F32 attention, 16.1% to F32 SIMT GEMMs and ~4.5% to the BF16
tensor GEMMs; against that run's 52.201 s denoise, the DiT attention alone is
90% of a denoise step at 512, and the quadratic extrapolation accounts for the
whole 768 step to within 1%.

Both engines run the same scalar tiled kernel here — one warp per query row,
per-lane BF16→FP32 FMA, shuffle reduce, lane-0 `exp`, two `__syncthreads` per
key row, no tensor cores (port `native/h3/h3_dit_gpu.cu:924-1015`, reference
`h3_gpu_cuda.cu:1418-1487`, the two functions line for line the same). That is
why the two engines' denoise times sit within 7% of each other: the same kernel
leaves the same hardware idle on both.

What that kernel is bound by is neither bandwidth nor FLOPs. Per call at 512
the grid is 544 × 56 = 30,464 CTAs, each staging 4,352 key rows × 512 B of K+V
= 2.23 MB, so 67.9 GB per call in 463 ms — an effective 147 GB/s, below both
the measured 236.8 GB/s DRAM rate and the 2,101 GB/s L2 read. The quantity that
does reproduce across shapes is the per-key-row cost: with the grid sized
`sequence/8 × heads`, both shapes land on the same ~1.3 µs per row (1.34 µs at
512 and 1.33 µs at 768 at the eight 256-thread CTAs an SM's 2,048-thread budget
allows — residency itself was not measured, and the shape-independence holds
for any residency). So each step costs about `sequence² × heads × 4.3e-10`
seconds: 8.2 s per call × 51 calls = 419 s at 18,432 tokens, against 418.44
measured.

At ~1.3 µs — over 3,000 cycles — for one staged 512-byte row, two barriers,
eight FMAs per lane and seven shuffles, the loop is almost entirely stall. That
reading pointed at the key-row load as the exposed part and at staging rows as
the fix; the measurement in the next section refutes half of it.

## The attention loop, restructured (measured)

Landed as commit `8e0cd0da` on `feat/h3-attention-loop`, carrying the kernel
change, the reproducer `tests/h3/attn_bm.cu` and its Makefile target.

| Arm | 4,352 tokens | 18,432 tokens | vs baseline |
|---|---:|---:|---:|
| baseline | 427.5 ms | 7,721.4 ms | — |
| 8 key rows staged per barrier | 389.6 ms | 6,986.6 ms | −8 to −9% |
| query row held in registers | 355.8 ms | 6,411.0 ms | −17% |
| both | 314.0 ms | 5,641.9 ms | −26.6% |

Every one of those numbers is `tests/h3/attn_bm.cu` on the Spark, one shape per
line, five calls at 4,352 tokens and two at 18,432, and every arm printed the
same output hash (`c6196e81bc4634e0` and `5c1e3810028a8fa5`), so the
restructure is bit-identical rather than merely close. That is what makes the
comparison valid: only staging and load placement moved, and each row keeps the
reference's arithmetic, reduction order and lane-0 softmax.

The KEYS sweep also says what the per-row cost is *not*. Staging key rows
recovered 8 to 9%, not the several-fold the exposed-load reading predicted, so
the key-row load was never the dominant term; hoisting the query row was worth
twice as much on its own. The remainder — about 73% of the original cost — is
still unattributed: the five-step shuffle reduction, the per-row softmax chain
on lane 0, and the shared-memory reads are what is left.

End to end on the same job (768×768, 107 frames, 2 steps, seed 42), with the
change built into `h3-rs` by `make h3-rs` and the repo's own `native_test`
passing on the rebuilt kernel:

|---|---:|---:|---:|
| TEXT | 28.479 s | 27.657 s | 28.42 s |
| LOAD | 7.234 s | 7.718 s | 20.092 s |
| DENOISE, 2 evals | 836.886 s | 617.244 s | 902.486 s |
| per step | 418.44 s | 308.62 s | 451.24 s |
| AUDIO | 2.587 s | 2.601 s | 3.065 s |

| Total, TEXT line to exit | 1,093.885 s | 875.212 s | 1,173.955 s |

The denoise gains 26.2% and the job 20.0%, and the render is still
byte-identical to the reference engine's
(`69816f7f4683d41b1c677e1e6028b36294ca8a87e77efba78c6056a3154a16f4`), so none
of that came from a visible output change. Against the reference the port is now
25.4% faster over the text-encoder-line-to-exit window (875.212 s against
1,173.955 s), which is the like-for-like figure.

The lever for the default path is therefore the loop's structure, not tensor
cores: an `mma`-based version of an unpipelined loop inherits its stalls, and it
cannot be bit-identical, since the reduction tree changes. The operator refused
that trade for the released path on 2026-10-27 ("we will not accept it"), so
every lever on the default path has to keep each row's arithmetic, its
reduction order and the lane-0 softmax. A tensor-core attention is added
separately, behind a switch that defaults to off, so it can be benchmarked
against the scalar kernel; it is a measurement arm and never the default.

## Rows per warp (the next lever, measured)

The reference gives each warp one query row. Every key row a warp reads is then
used once, and the barrier pair that publishes it is paid once per row. Giving a
warp `H3D_ATTENTION_ROWS` rows makes the staged key rows and the barrier pair
serve that many rows; each row still runs its own four-lane partial product, the
reference's shuffle tree, and its own lane-0 online softmax, so the arithmetic
per row is untouched and the output hash gates the change.

Three rounds each, `tests/h3/attn_bm.cu` on the Spark, five calls at 4,352
tokens and two at 18,432. The control is the binary built from the landed kernel
before the rewrite; `ROWS=1` is the rewrite configured back to the reference's
mapping, so the change can be separated from the codegen drift it introduced.

| Arm | 4,352 tokens | 18,432 tokens | vs 1 row |
|---|---:|---:|---:|
| control, landed binary | 308.9 ms | 5,575.0 ms | — |
| 1 row per warp | 311.5, 314.1 | 5,595.3, 5,606.0, 5,648.6 | — |
| 2 rows per warp (adopted) | 293.9, 295.2, 297.0 | 5,276.6, 5,277.1, 5,318.5 | −5.6% / −5.8% |
| 4 rows per warp | 298.3, 298.2, 300.5 | 5,321.0, 5,321.8, 5,363.6 | −4.4% / −4.9% |

Two rows is the knee: four rows is worse at both shapes, and the run-to-run
spread is under 1%. Against the landed binary the gain is 4.4% at 4,352 and
5.1% at 18,432, which is the conservative pair of numbers to quote, because the
rewrite at `ROWS=1` is itself about 1% slower than the binary it replaces: that
1% is codegen drift, not an effect of the change. Every arm in every round
printed the same output hash (`c6196e81bc4634e0` and `5c1e3810028a8fa5`) as the
control did, so the change is bit-identical, and `tests/h3/native_test` passes
on the rebuilt kernel, including its tiled-attention axis gate. ptxas reports no
spills at any width: 38 registers at one row, 48 at two, 72 at four, 8 KiB of
shared memory and a zero-byte stack frame in all three.

## The video VAE's F32 attention (measured)

The same treatment applies to `h3d_attention_tiled_f32_kernel<64>`, the video
VAE decoder's attention (`crates/ds4-core/src/minimax_h3/vae_video.rs` calls
`h3d_sdpa_f32` once per layer per tile: 36 layers, 12 tiles, 432 calls per
decode). It was the second-largest kernel in the profile at 24.4% of GPU time,
432 instances, 54.78 ms average, and it still staged one key row per barrier
pair, re-read its query row from global for every key row, and gave each warp
one query row. Its tile is `CHUNK_LATENT_TIME * latent_h * latent_w + SUFFIX`
rows at 32 heads of 64 dimensions, so 16,133 rows for the 768 job and 7,173 rows
for the 512 one; the reproducer is `tests/h3/attn_f32_bm.cu`.

BF16 one at the same shape: 16,133 rows at 32 heads of 64 take 1.70 s, where the
BF16 kernel took 5.28 s for 18,432 rows at 56 heads of 128, and the reference's
F32 loop was 3.10 s here. The task is latency, not arithmetic, in both cases.

## The tensor-core attention, as a switch

`H3_DIT_ATTENTION_MMA` selects an `mma.m16n8k16` flash attention instead of the
scalar kernel. Opt-in only, off by default — the operator's decision of
2026-10-27 — so it is a measurement arm and never a path a gate reads. It is read
once, in `h3d_create`; unset, or `0`, leaves the byte-exact kernel in place.

It covers exactly one entry point, `h3d_sdpa`, the DiT's BF16 attention across
all 50 blocks and the 2 token refiner. The F32 VAE attention (`h3d_sdpa_f32`)
and the causal F32 path are separate and stay exact in both arms, which is why
`FRAMES` does not move.

### What it is built from

The step, the ldmatrix pair and the BF16 pair are mirrored from this repo's own
mma attention, `cuda/ds41_attn_mma.cuh:144-157`, and the Q fragments, the
accumulator layout and the P-to-A packing from `:206-277`. One simplification
holds for H3: a warp owns all 128 key dimensions, so a row's softmax statistics
never cross a warp and ds41's partial-score exchange is not needed.

`ptxas` reports 168 registers, no spills, no stack, 34,816 bytes of static
shared memory, against the scalar kernel's 48 registers and 8,192 bytes.

### Three named deviations

1. The scores accumulate through `mma`, so the reduction tree replaces the
   scalar kernel's four-element lane partial and its five-step shuffle.
2. The online softmax takes one maximum per 64-key tile instead of rescaling on
   every key row.
3. P rounds to BF16 for the second `mma`; the scalar path keeps it in FP32.

Scores, the running maximum and sum, and the output accumulator stay FP32, so
the arithmetic is the scalar kernel's in kind and differs only in order. That
distinction is the whole reason the switch exists rather than a replacement: the
gate below is byte identity, and no `mma` reduction tree can hold it.

### Output quality

Job A's two renders share their shape and encoder: 768x768, H.264, 107 frames at
4.458 s, 32 kHz stereo AAC, 141 audio frames each. Against the gate render the
switch-on render measures PSNR y 42.75 dB, u 51.17 dB, v 50.36 dB, average
44.18 dB, minimum 40.11 dB, and SSIM Y 0.9829, U 0.9944, V 0.9946, all 0.9868.

At the kernel, the tensor arm against the scalar output is max absolute
2.4414062e-04 with rms 2.3465292e-05 at 4,352, and max 1.2207031e-04 with rms
1.1488895e-05 at 18,432, with 42.76 and 42.26 percent of values differing. That
is not last-bit rounding. The dominant cause is the third deviation: P carries
roughly 0.4 percent relative error once it rounds to BF16, and the scalar path
does not round it at all.

### Still open on this arm

No noise floor exists on this host for this kernel. Every benign configuration
change measured so far is bit-identical, so there is no established band inside
which the tensor arm's deviation could be called noise-class. The honest
statement is that the deviation is attributable — P's BF16 rounding plus the
reduction tree — but not yet bounded against a measured floor. A deliberately
benign reorder in the scalar kernel would supply one, and until it exists the
tensor arm's fitness is judged on the render, not on a band.

## Still open

- The remaining ~73% of the attention's per-row cost is no longer a guess: the
  ncu attribution below measures the binding resource as the shared-memory
  instruction stream (LSU 99.21% of peak), with the stalls split between
  short-scoreboard and MIO-throttle. The shuffle reduction and the lane-0
  softmax chain are not the binding limit, so the next probe is the
  shared-memory instruction count, not a wider cut of those chains.
- Tensor cores are an option, not the default. The operator refused the
  noise-floor trade for the released path on 2026-10-27 ("we will not accept
  it"), because an `mma` reduction tree changes the arithmetic order and so
  cannot hold the byte-exact gate; the default path is unchanged and its gate
  stays exactly as it is (the reproducer's output hash unmoved and the render
  sha256 equal to
  `69816f7f4683d41b1c677e1e6028b36294ca8a87e77efba78c6056a3154a16f4`). The
  operator then asked for a tensor-core attention as a switch, on a test tip of
  this branch, to benchmark it. So the `mma` path is added behind an explicit
  switch that defaults to off: a measurement arm, expected to differ from the
  gate's output, and therefore never the default. What remains for the default
  path is structural: shared-memory reads and bank conflicts, occupancy and
  register pressure, staging depth, the CTA order, rows per warp.
- ncu stall attribution: DONE 2026-10-27 on `h3d_attention_tiled_kernel` at
  18,432 tokens x 56 heads (kernel replay, one launch, no full-model process).
  `sm__inst_executed_pipe_lsu` is 99.21% of peak and `sm__throughput` takes the
  same 99.21%; FMA is 27.66%; issue-active is 59.90% and warps-active 83.25%.
  Stalls per issued instruction: short-scoreboard 4.77 and MIO-throttle 4.09,
  ahead of wait 2.14, not-selected 1.94 and barrier 1.52. Shared-memory bank
  conflicts are 616,776 on loads against 301,696,301 on stores. The kernel is
  bound by the shared-memory instruction stream, not by FLOPs, barriers or the
  lane-0 softmax chain. 48 registers per thread and 8.19 KB of static shared
  memory cap occupancy at 5 blocks (registers) against 6 (warps) and 11
  (shared).
- One unsourced cell of the per-step law remains: 32,256 tokens, and the
  1,344×768 shape generally, which no retained run covers. The 8,192-token cell
  is now measured by the attention sweep above.
