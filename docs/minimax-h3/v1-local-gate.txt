MiniMax-H3 local v1 wire gate (stand-in renderer)
=================================================

Date: 2026-10-25. Box: RTX 4070 SUPER 12 GB, 31 GB RAM, 28 cores.
Binary: target/debug/h3-server-rs, built from the worktree at HEAD fca63484
plus P15.1-P15.4 (the local v1 swap, uncommitted).
Contract: docs/minimax-h3/local-v1-contract.md.

What this gate proves: the three routes exist and nothing else does; the five
field SGLang body reaches a resolved plan (task, canvas, duration, frames,
seed, keyframe); the task record and the MP4 travel as the contract says; and
every documented refusal comes back with its code over a real socket.

What it does not prove: nothing about the engine. The renderer here is a
stand-in that writes a real H.264/AAC clip with ffmpeg from the argv the bridge
builds, so it proves the wire and the mapping, not h3 output. The real engine
gate is P15.6, on the host that holds the weights.

The stand-in renderer, verbatim (/tmp/h3-standin.sh, outside the repo):

  #!/usr/bin/env bash
  set -euo pipefail
  out=""; w=""; h=""; s=""; seed=""; first=""; last=""
  while [ $# -gt 0 ]; do
    case "$1" in
      -p) shift 2 ;;
      --width) w=$2; shift 2 ;;
      --height) h=$2; shift 2 ;;
      --seconds) s=$2; shift 2 ;;
      --seed) seed=$2; shift 2 ;;
      --first-frame) first=$2; shift 2 ;;
      --last-frame) last=$2; shift 2 ;;
      -o) out=$2; shift 2 ;;
      *) shift ;;
    esac
  done
  { printf 'argv: width=%s height=%s seconds=%s seed=%s first=%s last=%s out=%s\n' \
      "$w" "$h" "$s" "$seed" "${first:--}" "${last:--}" "$out"
    if [ -n "$first" ]; then
      printf 'first-frame: exists=%s bytes=%s header=%s\n' \
        "$([ -f "$first" ] && echo yes || echo no)" "$(wc -c <"$first")" \
        "$(head -c 8 "$first" | od -An -tx1 | tr -d ' \n')"
    fi
  } >>"${H3_STANDIN_LOG:-/dev/null}"
  ffmpeg -v error -y \
    -f lavfi -i "testsrc=size=${w}x${h}:rate=24:duration=${s}" \
    -f lavfi -i "anullsrc=r=32000:cl=mono" \
    -t "$s" -c:v libx264 -preset ultrafast -pix_fmt yuv420p -c:a aac -shortest \
    "$out"

The keyframe for the FL2VA call is a 960x540 PNG (18680 bytes) made with
ffmpeg, so `aspect_ratio: "auto"` has a 16:9 anchor to read.

The render did not finish. Two attempts (33 minutes, then 9 minutes on an
instrumented build) were stopped by the operator; no MP4 was written and no
error was raised. Measurements taken during the first attempt, all from this
host: GPU 96 % at 2405-2411 MHz, 80-88 W, 82 C; the process had read 48.8 GB
from disk and stopped reading; the h3-engine thread held ~98 % of one core;
nvidia-smi showed no other compute process.

Why the shape is hours: the per-step cost measured on this box is
40.2 s at 1344x576/22 f (4,536 tokens) and 112.9 s at 1344x576/39 f (9,072
tokens) - 2.8x for 2x, exponent ~1.5 (post-port-phases.md:905, :975). The gate
shape, 1344x768/107 f, is 32,256 tokens, 3.6x the larger of those, so the step
lands near 10-13 minutes and 20 steps is hours. The cheatsheet's 11.6-minute
row for this shape assumed 104 TFLOP/s and is contradicted by that pair.

Two gaps came out of the attempt, both closed in the worktree:

- Observability: `h3.c:649-676` reports `on_progress(phase, completed, total)`
  and the reference CLI prints it; the in-process engine installed no sink, so
  a render was silent until the MP4 landed. engine.rs now prints
  `STEP n/N seconds=<step> total=<since denoise start>` per evaluated step.
- The renderer CLI: `h3-rs` parsed none of the reference flags
  (`main.c:51-56`, `:333-338`, `:429-490`), so only `--model-dir` could serve a
  reference. It now parses all six, switches to `Ref2VA` (`h3.c:872-875`),
  refuses anchors with references (`h3.c:597-600`), and shares
  `reference::prepare_set` with the engine.

Not covered here: any MP4 from the real engine through /v1, the fl2va and
ref2va live renders, and the two audio set rules inside the engine. The
shortest honest wire render this contract can express is 768P, 4 s,
`--steps 2`: about two steps plus a load and a VAE decode, roughly 30-40
minutes, because `short_edge` is fixed at 768 and 4 s is the minimum duration.

Reading the transcript
----------------------

- `samples=138667` is the two soundtracks summed: 74,667 cut from the video at
  56 output frames (`h3.c:1144-1147`) plus 64,000 from `ref.mp3`, against the
  480,000-sample set budget.
- The 2-second floor reads the decoded reference frames
  (`reference.rs:305-312`, `h3.c:1144-1151`), and the reader trims decoded
  frames to 5+17n (`h3_ffmpeg.c:362`). A 2.000 s reference video is 48 frames,
  trims to 39, and is refused by this same rule; the fixture was widened to
  3.0 s (72 frames, 56 after the output cap) and the render ran. The reference
  behaves identically, so this is a fixture lesson, not a deviation.
- `DENOISE` is a third per-step measurement and it does not agree with the
  pair recorded from the stopped 768P attempt: 47.75 s/step at 17,408 tokens
  (512x512, 56 frames), 5.37 s/step at 7,168 tokens (512x512, 22 frames), and
  40.2 s at 4,536 / 112.9 s at 9,072 (1344x576, earlier). 2.43x tokens cost
  8.9x per step in the new pair and 2x cost 2.8x in the old one, so the step
  cost is not a function of token count alone and a 768P budget still needs
  its own measurement.
- Not covered: the served surface. A ref2va body cannot ask for 56 frames (the
  contract's floor is 4 s = 107 frames) and 512x512 is a CLI canvas, so this
  proves the engine path, not the wire. A served ref2va render is the same
  768P gate as P15.6.

## 2026-10-25 — the first completed served render (t2va, 768x768, --steps 2)

The P15.5 gate proved the wire with a stand-in renderer; this run is the same
surface with the real engine and the real checkpoint, and it completed.

- Request: `task t2va`, prompt "A red kite lifts off a grey beach at dawn, the
  camera tracks it rising over wet sand. Wind, distant surf, and a low
  sustained drone underneath.", `target {short_edge 768, aspect_ratio 1:1,
  duration_seconds 4}`, seed 1, server `--steps 2 --max-jobs 2` on the Spark.
- Answer: `{"id":"video_1"}`, then `in_progress`, then `completed`; created
  1792951693, completed 1792953021, so 1328 s wall (22 min 8 s) for 107
  frames. A second request (video_2, fl2va 16:9) was accepted at 1792952173
  and its first-frame copy appeared on disk at 19:16, but that copy is written
  while the request is prepared (`crates/ds4-server/src/h3_video.rs:287`) and
  the render itself waits: the engine is one thread serving calls in order
  (`crates/ds4-core/src/minimax_h3/engine.rs:589-601`), so this 1328 s is a
  solo render.
- Record: `size 768x768`, `frames 107`, `aspect_ratio 1:1`, `duration_seconds
  4`.
- File: `~/h3-api/out/video_1.mp4`, 900,652 bytes; `GET
  /v1/videos/video_1/content` returned the same bytes. ffprobe: h264 768x768,
  24 fps, 107 frames, aac 32 kHz stereo, 4.458 s.
- Quality at two steps is a preview, not a deliverable: the frame is a smooth
  gradient with a small red kite, and the kite moves a few pixels over the
  clip. The reference's own four-pass mode measures SSIM 0.556 against a
  29-pass render (README:245-250), and two passes is below that.
- Concurrency lesson: `--max-jobs` bounds the job store (completed jobs
  included) but not throughput. The in-process engine renders one request at a
  time, and a queued job still reports `in_progress` once its render thread has
  started, so the status a client sees does not distinguish waiting from
  rendering. At two steps and 768x768 that one job cost 1328 s on its own.

## 2026-10-25 — the load experiment: faster, and wrong

The clean A/B put the port 118 s behind the reference at one shape, and 94 s
of that was the checkpoint load (116.1 s against 21.9 s). Two traces with the
same bytes (126,551 MB host-to-device, 2,210 copies) showed the reference's
copies costing 4.44 s as 2,219 synchronous `cudaMemcpy` calls while the port's
cost 105.4 s as 2,210 `cudaMemcpyAsync` calls from a pageable source.

Two changes were tried, both reverted:

1. A blocking copy for checkpoint weights (`h3d_upload_blocking`,
   `cudaMemcpy` instead of `cudaMemcpyAsync`). Load 116.07 -> 106.65 s, wall
   560.04 -> 625.98 s. Small, and the wall got worse.
2. Reading each tensor into an anonymous buffer and copying from there, which
   is the reference's own structure (`h3_weights.c:144-186`,
   `h3_gpu_cuda.cu:375-425`). Load 106.65 -> 23.65 s, wall 467.72 s, which is
   within 8% of the reference's 433.39 s.

Both changes altered the output. The port's committed output is
byte-identical to the reference at this shape
(`74d862fef9dc904d69c20f3dffec74f4`); with either change it is
`7991a015b1a161ec95d6b3f1aae8e3fc`, and the decoded video and audio MD5s
differ too, so the frames themselves changed. The copy path must not change
numerics, so the difference is unexplained and the change is out until it is.

The open question for the next unit: why does copying the same bytes through
`cudaMemcpy` (or through an anonymous staging buffer) change the result at
all? Candidates to test before the speed can be kept: the legacy default
stream versus the non-blocking context stream (`cudaStreamCreateWithFlags`),
and whether any load-time kernel reads a tensor the copy is still writing.
