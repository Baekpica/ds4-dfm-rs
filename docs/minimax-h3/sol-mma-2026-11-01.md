# The sparse attention, tensor-core (2026-11-01)

Phase D, fourth pass. `ltx-attn-mma-2026-11-01.md` closed the dense core and left
the block at 638.0 ms with **430.8 ms of it - 67.5 % - in the Sol-Attn sparse
forward**, the token-major re-expression of a kernel the tower runs in 30.5 ms
on the same shape. This is that kernel, ported.

**Result: stage 2's denoise falls from 94.046 s to 35.519 s, -62.2 %, and the
block falls from 638.0 ms to 231.7 ms. The picture at 0.992 SSIM / 48.4 dB is
the dense arm's own clip, one switch apart** - this arm changes the arithmetic
order, not the function.

Arm: `H3_SOL_MMA=1` (`17c1dd5a`), stacked with `H3_LTX_ATTN_MMA=1`. Default
unchanged: both scalar kernels stay the default and the one-block golden's
bit-exact reference.

## 1. What was ported, and how little it was

`h3d_sol_forward_kernel` (`native/h3/h3_dit_gpu.cu:7094`) already walks exactly
the right structure: one CTA per 64-row query block and head, one warp per 16 of
those rows, a mask word's `GROUP = 32` KV blocks folded in a single `P @ vc`
pass, then that group's exact blocks in increasing block order - `fwd.py:88-173`
as the Spark release enforces it. It reads head-major `[heads][rows][128]`.

The refiner's operands are token-major, and its plan is already in the right
layout: `kc`/`vc` come from `h3d_sol_ltx_pool_kernel` as `[head][block][128]`,
the mask is `[q_block][head][word]`, and the output write was token-major even
in the tower's kernel. So the port is **three index expressions and nothing
else**: the two query-row reads and the staged key/value row in
`h3d_sol_ltx_stage`. The diff against the tower's kernel, whole:

| the tower's text | the port's text |
| --- | --- |
| `query + (head * sequence + row) * 128` | `query + (row * heads + head) * 128` |
| `source + (head * rows + at) * 128` (key, value) | `source + (at * heads + head) * 128` |

`h3d_sol_ltx_forward_mma` (`:8188`) validates what `h3d_sol_ltx_forward`
validates - the same buffer sizes and the same `h3d_sol_check` on the plan - and
adds the kernel's one restriction, head dimension 128, which Sol-Attn already
requires (`interface.py:29-30`).

## 2. The two arms on one plan

`tests/h3/sol_ltx_bm 16128 3`, both arms over the **same plan** built by the real
`h3d_sol_ltx_search`, one warm-up pass each, at each of the release's three
taus (`sol_attention.py:18`):

| tau | realized exact blocks | scalar | MMA | gain |
| --- | ---: | ---: | ---: | ---: |
| 1.00 | 16.70 % | 418.398 ms, 1.86 TFLOPS | 12.112 ms, 64.34 TFLOPS | 34.6x |
| 1.25 | 11.47 % | 300.450 ms, 1.85 TFLOPS | 9.313 ms, 59.77 TFLOPS | 32.3x |
| 1.50 | 7.64 % | 213.903 ms, 1.84 TFLOPS | 7.172 ms, 54.80 TFLOPS | 29.8x |

The rates are computed on the work the mask actually buys - an exact block is
`4 * 64 * 64 * 128` FLOPs, a folded group `4 * 64 * 32 * 128` - so they are the
kernel's own efficiency, not a dense-shape figure it never runs at. The scalar
column reproduces the 430.8 ms the block profile attributes to the same forward
(418.4 ms at tau 1.0, the first step's tau).

The realized shares have their own check: a block is routed exact when its score
clears `mean + tau * std` of the 252 block scores, so a roughly normal score
distribution predicts 15.9 / 10.6 / 6.7 % exact at the three taus. Measured:
16.70 / 11.47 / 7.64 %. The small excess is the diagonal band, which the route
kernel forces exact regardless of the threshold (`sol_attn/preprocess.py`
`diag` policy).

## 3. What they compute, and how far apart

| tau | differing | rel_rms | max_abs | output scale | rows with a sign-flipped 128-sum |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1.00 | 72.18 % | 9.388e-5 | 4.883e-4 | 0.0952 | 488 of 516,096 |
| 1.25 | 72.82 % | 9.165e-5 | 4.883e-4 | 0.0952 | 444 of 516,096 |
| 1.50 | 73.24 % | 9.039e-5 | 4.883e-4 | 0.0942 | 435 of 516,096 |

`max_abs` is **exactly one BF16 ulp** at these magnitudes (ulp(0.095) = 2^-11 =
4.883e-4), and `rel_rms / scale` = 9.9e-4 is 0.2 ulp: the bulk of the difference
is the fragments' rounding, and no element is off by more than one count. 0.09 %
of the rows have a 128-wide sum whose sign the last bits decide - the same
class of row, at the same rate, as the dense arm's.

Correction to `ltx-attn-mma-2026-11-01.md` §3: that section quoted "a BF16 ulp of
7.8e-3 at 0.096". The ulp there is 4.883e-4; its `max_abs` of 4.883e-4 was
therefore one ulp exactly, not a fraction of one. The conclusion - a rounding
difference, not a different function - is unchanged; the arithmetic that stated
it was not.

-23.5 / -19.2 / -15.8 s a step. 430.8 ms of Sol forward per block x 48 blocks is
20.68 s of a step, and the arm's own forward lap measures 12.63 ms, which is
0.61 s - a step kept 20.1 s of the 20.7 predicted.

One observation, and it is not part of the arm: step 0 is now within 0.23 s of
step 2. The earlier receipts measured step 0 costing ~7.9 s more, attributed to
the lazy first touch of the 34.58 GiB weight file - 0.773 GB/block at 4.7 GB/s.
That whole file is exactly 34.58 GiB, so the reading was a per-process read of
it, and in this run the file had been read by the control run nine minutes
earlier and was still resident. **A cold-file run would pay it again**; it was
not isolated here (that needs a page-cache drop, which needs root), so it is
stated as the likely reading and not as a result.

Two arms together: **-72.1 % on the block, -70.8 % on the denoise**, and the VAE
decode (15.1 s) is now 43 % of a run's stage 2.

One honest gap between the bench and the product: the bench's synthetic operands
realize 16.7 / 11.5 / 7.6 % exact and the refiner's own operands route denser.
The arm's lap is 12.63 ms against the 9.53 ms a step-weighted mean of the three
bench points predicts, and the fold-plus-slope fit of the bench
(`ms = 3.01 + 0.545 * share%`) puts the realized share at ~17.6 % on average.
That is the direction real video latents should push - neighbouring tokens are
correlated, so a query block and a nearby block's mean align - and it means the
bench's gain is the conservative one, not the optimistic one. The share itself
is not printed by the run; the number above is inferred from the timing model,
not read from the plan.

## 6. What is left in the block

At 231.7 ms, in order:

| item | ms | share |
| --- | ---: | ---: |
| projections, the four video and AV instances | 82.3 | 35.5 % |
| video feed-forward | 65.7 | 28.3 % |
| **the AV pair's two cores** (head dim 64) | 33.6 | 14.5 % |
| norms, rotary, search, out-projections, gates | 27.9 | 12.0 % |
| video self core (Sol, all 144) | 13.8 | 6.0 % |
| text cross core (dense MMA) | 5.7 | 2.5 % |
| audio, all of it | 2.8 | 1.2 % |

- The AV cores are the last kernel on a slow path: 33.6 ms at 0.8-1.25 TFLOPS
  because `H3D_MMA_HD` is cut at 128 and those two attentions are 64 wide. A
  64-wide fragment set is the same port one enum down.
- The projections are already at the tensor cores' own rate - 92.5 TFLOPS
  measured for the block's 34 projections - so what remains there is
  algorithmic, not a kernel.
- The video feed-forward is 48.5 ms of GEMM plus its GELU and gate.
- The search is now 2.84 ms against the forward's 12.63: routing is no longer
  free relative to what it routes (0.41 s a recipe, 22 % of the sparse cost).
